# OpenChoreo: CNCF Cloud-Native Internal Developer Platform and Agentic AI Practice

In Chapter 11, we conducted an in-depth examination of **Backstage**, the de facto open-source standard for Internal Developer Portals (IDPs). Through its Software Catalog, Software Templates (Scaffolder), TechDocs, and rich plugin ecosystem, Backstage elegantly resolves the service discovery and cognitive overload bottlenecks that plague organizations scaling microservices.

Yet, after platform teams enthusiastically introduce Backstage into their organizations, they frequently collide with a deeper architectural reality:

> **"Backstage is an exceptional developer portal, but it is not an execution platform engine."**

Backstage illuminates what services exist, visualizes ownership topologies, and scaffolds code via pull requests; however, it does not manage the runtime lifecycle of Kubernetes resources, dynamic environment isolation, traffic splitting, service mesh security policies, or automated telemetry pipelines. To bridge this vast chasm between the "portal" and the "underlying infrastructure," platform engineering teams often write tens of thousands of lines of fragile "glue code," stitching together Backstage, ArgoCD, Crossplane, Terraform, Prometheus, and Envoy. This homemade patchwork is brittle, agonizing to upgrade, and frequently turns the platform team into an operational bottleneck.

Furthermore, with the dramatic ascent of **Agentic AI** and the **Model Context Protocol (MCP)**, organizations urgently require a **modern control plane that empowers autonomous AI agents to safely perceive cluster state, reason with precise telemetry, and execute governed remediation loops within cloud-native environments**.

Enter **OpenChoreo**. Accepted into the **Cloud Native Computing Foundation (CNCF)** as an open-source Sandbox project in 2024 (originated from WSO2's enterprise cloud-native experience; documentation: [https://openchoreo.dev/docs/](https://openchoreo.dev/docs/)), OpenChoreo was designed from the ground up to solve this exact platform engineering disconnect.

This chapter explores OpenChoreo in detail: its **Multi-Plane Architecture**, the **declarative division of responsibilities** between developers and platform engineers, its seamless synergy with **Backstage**, and its pioneering **native integration of MCP and autonomous operational agents (SRE and FinOps Agents)**.

# Why OpenChoreo? Tearing Down the Kubernetes "YAML Wall"

Kubernetes has become the undisputed distributed operating system of modern cloud infrastructure. However, for application engineers, its steep learning curve often feels like an operational nightmare.

```mermaid

    end
```

## Pain Point 1: Cognitive Overload from Business Logic to Infrastructure Plumbing
A typical Python FastAPI or Go microservice might only require a few hundred lines of business code. But to deploy it reliably onto a production Kubernetes cluster, developers are forced to write and maintain:

* `Deployment` (probes, resource requests/limits, lifecycle hooks)
* `Service` and `HTTPRoute` / `Ingress` (load balancing, TLS certificates)
* `HorizontalPodAutoscaler` (HPA autoscaling metrics)
* `NetworkPolicy` (zero-trust pod-to-pod isolation)
* `PodDisruptionBudget` (high-availability maintenance protection)

This is commonly known as **"The YAML Wall."** Developers burn valuable engineering cycles copy-pasting esoteric Kubernetes manifests. If a single security parameter is omitted (such as `runAsNonRoot` or proper memory constraints), cluster stability is jeopardized.

## Pain Point 2: The Dilemma Between Black-Box PaaS and Raw Kubernetes
To shield developers, teams historically adopted PaaS solutions (like Heroku or custom internal wrappers). However, black-box PaaS architectures obscure underlying mechanics; as workloads mature and demand canary deployments, advanced mesh tuning, or hybrid cloud migrations, the PaaS quickly becomes a restrictive dead end.

**OpenChoreo's guiding philosophy: "Augment, not hide, Kubernetes."**

* It is **Kubernetes-native**: All platform abstractions are implemented as Custom Resource Definitions (CRDs), utilizing the Kubernetes API as the authoritative System of Record.
* It enforces **GitOps**: Developers express high-level application intent (`Component`), while platform teams enforce organizational standards (`ComponentType`). OpenChoreo reconciles these inputs into fully compliant, secure underlying manifests.

## 1. Control Plane
The Control Plane is the brain of OpenChoreo, operating inside the Kubernetes cluster as a suite of lightweight controllers and CRDs. Its responsibilities include:

* Watching developer `Component` definitions and platform `ClusterComponentType` templates;
* Evaluating and binding extensible `Trait` policies (e.g., autoscaling, rate-limiting);
* Validating parameter inputs against security guardrails and schemas;
* Generating downstream Kubernetes objects (`Deployment`, `Service`, Envoy `HTTPRoute`, `NetworkPolicy`);
* Orchestrating release promotions across environments (`DeploymentPipeline`).

## 2. Build & Workflow Plane
The Build & Workflow Plane automates code-to-artifact pipelines directly on Kubernetes without relying on opaque external CI servers:

* **Source-to-Image Pipeline**: Managed via `Workflow` and `WorkflowRun` resources, triggering cloud-native container builds (via Buildpacks or Kaniko/Tekton);
* **Artifact Integrity**: Produces immutable container images tagged by cryptographic SHA-256 digests, establishing the foundation for `ComponentRelease` entities.

## 3. Data Plane
The Data Plane is where application containers run, spanning single or multiple target clusters:

* **Networking & Gateways**: Built on **Envoy Gateway** (adhering to the Kubernetes Gateway API standard) and **Cilium**, enabling canary releases, mTLS encryption, and fine-grained network policies.
* **Cell-Based Architecture**: Workloads, caches, and endpoints are organized into cohesive, bounded "Cells," radically restricting blast radiuses during incidents.

## 4. Experience Plane
Provides unified interfaces for engineers:

* **Backstage IDP Portal**: Comprehensive graphical dashboards via the official OpenChoreo Backstage Plugin.
* **`occ` CLI**: High-velocity terminal tooling for developers.
* **Model Context Protocol (MCP) Server**: Standardized protocol endpoints allowing autonomous AI agents to query topology and runtime health.

## 5. Observability Plane
Built natively on OpenTelemetry (OTel), aggregating metrics, logs, and distributed traces into unified query APIs for human operators and AI agents alike.

## 6. Agentic Plane
Hosts autonomous operational AI agents (such as SRE Root Cause Analysis agents, FinOps cost optimization agents, and developer portal assistants). The Agentic Plane consumes normalized telemetry from the Observability Plane, exchanges contextual graph data via MCP servers, and submits declarative proposals and PRs to the Control Plane.

## 1. Developer View: Declarative `Component`

Developers maintain a clean `component.yaml` in their repository root:

```yaml
apiVersion: openchoreo.dev/v1alpha1
kind: Component
metadata:
  name: payment-service
  namespace: ecommerce-project
spec:
  # Reference the platform-curated Golden Path template
  type: microservice-rest
  
  source:
    git:
      url: https://github.com/acme-corp/payment-service.git
      branch: main
    build:
      dockerfile: ./Dockerfile
      
  endpoints:
    - name: api
      port: 8080
      type: REST
      schema: ./openapi.yaml     # Linked OpenAPI specification
      visibility: internal
      
  env:
    - name: LOG_LEVEL
      value: "INFO"
    - name: DB_CONNECTION_SECRET
      valueFrom:
        secretKeyRef:
          name: payment-db-credentials
          key: connection-string

  # Composable traits: add operational capabilities without altering templates
  traits:
    - type: auto-scaler
      properties:
        minReplicas: 2
        maxReplicas: 10
        cpuUtilizationPercentage: 75
    - type: rate-limiter
      properties:
        requestsPerSecond: 500
```

> **Note & Synergy with Chapter 11 API Catalog**:
> 1. Developers never specify Kubernetes Selectors, Pod Specs, Affinities, or Envoy routing manifests! Everything is synthesized based on `type: microservice-rest`.
> 2. The `schema: ./openapi.yaml` field under `endpoints`: OpenChoreo utilizes this not only for Envoy Gateway routing validation, but also as the single source of truth for **contract-driven platform engineering**. The control plane automatically synchronizes this specification into the Backstage API Catalog explored in Chapter 11.

## 3. Extensible Capabilities: Composable `Trait` Architecture

In large engineering organizations, component requirements diverge rapidly. If platform engineers relied exclusively on `ClusterComponentType`, they would inevitably suffer from **"Template Explosion"**—creating endless variations such as `microservice-rest-autoscale`, `microservice-rest-ratelimited`, and `microservice-rest-gpu`.

OpenChoreo resolves this via **`Trait`** resources. A `Trait` encapsulates an orthogonal operational concern (e.g., Horizontal Pod Autoscaling, Envoy Rate Limiting, Cilium Egress filtering, or Scheduled Backups):

```yaml
apiVersion: openchoreo.dev/v1alpha1
kind: Trait
metadata:
  name: auto-scaler
spec:
  appliesToWorkloads:
    - "microservice-rest"
    - "worker-service"
  propertiesSchema:
    openAPIV3Schema:
      type: object
      required: ["minReplicas", "maxReplicas"]
      properties:
        minReplicas:
          type: integer
          minimum: 1
        maxReplicas:
          type: integer
          maximum: 50
        cpuUtilizationPercentage:
          type: integer
          default: 80
  resources:
    - template:
        apiVersion: autoscaling/v2
        kind: HorizontalPodAutoscaler
        metadata:
          name: "{{ .component.metadata.name }}-hpa"
        spec:
          scaleTargetRef:
            apiVersion: apps/v1
            kind: Deployment
            name: "{{ .component.metadata.name }}"
          minReplicas: {{ .properties.minReplicas }}
          maxReplicas: {{ .properties.maxReplicas }}
          metrics:
            - type: Resource
              resource:
                name: cpu
                target:
                  type: Utilization
                  averageUtilization: {{ .properties.cpuUtilizationPercentage }}
```

Through traits, platform engineers define governance policies once, allowing developers to compose capabilities dynamically like LEGO blocks.

## 4. The Immutable Release Lifecycle: ComponentRelease to ReleaseBinding

One of OpenChoreo's most robust enterprise patterns is its **three-stage immutable release lifecycle**. Traditional CI/CD setups often suffer from configuration drift across environments: a container built for `staging` is re-templated in `production` with untested YAML parameters, triggering unexpected outages.

OpenChoreo enforces deterministic, zero-drift promotions via cryptographic immutability:

```mermaid
flowchart TD
    subgraph BuildStage["1. Build & Artifact Freezing"]
        GitCommit["Git Commit (main)"] -->|Trigger WorkflowRun| KanikoBuild["Workflow Engine (Container Build)"]
        KanikoBuild -->|Produce OCI Image with SHA-256 Digest| Registry["OCI Container Registry"]
        Registry --> CompRelease["ComponentRelease (CRD)<br/>• Immutable Image Digest<br/>• Frozen Component Spec<br/>• Cryptographic Hash"]
    end

    subgraph RenderStage["2. Environment Rendering & Promotion"]
        CompRelease --> Pipeline["DeploymentPipeline Engine"]
        Pipeline -->|Promote to Target Env| RenderEngine["Template Engine + Secret Ref"]
        RenderEngine -->|Combine Release + Staging Params| RenderStaging["RenderedRelease (Staging)"]
        RenderEngine -->|Combine Release + Production Params| RenderProd["RenderedRelease (Production)"]
    end

    subgraph ExecutionStage["3. Runtime Binding (Data Plane)"]
        RenderStaging --> BindStaging["ReleaseBinding (Staging Namespace)"]
        RenderProd --> Gatekeeper{"Audited Gatekeeper<br/>(Canary / Dual-Key / AI)"}
        Gatekeeper -->|Approved| BindProd["ReleaseBinding (Production Namespace)"]
    end
```

1. **`ComponentRelease` (Frozen Build)**:
   When code merges, OpenChoreo triggers a `WorkflowRun`. Once tested and containerized, it generates a `ComponentRelease`. This object freezes the container image's immutable SHA-256 digest, OpenAPI contract, and base parameters into a write-once record.
2. **`RenderedRelease` (Environment-Specific Manifests)**:
   When promoting across a `DeploymentPipeline` (e.g., from `dev` → `staging` → `production`), the control plane merges the frozen `ComponentRelease` with target environment parameters and encrypted secrets (`SecretReference`), producing a deterministic `RenderedRelease`.
3. **`ReleaseBinding` (Active Cluster State)**:
   The `ReleaseBinding` links the `RenderedRelease` to the physical Kubernetes namespace on the target Data Plane. Rolling back production requires merely updating the pointer to a previous known-good `ReleaseBinding`, restoring identical manifests within milliseconds without rebuilding images.

Benefits of this clean boundary:

* When platform engineers update enterprise security standards in `ClusterComponentType`, all consuming microservices automatically inherit the new compliance posture upon reconciliation—without forcing developers to rewrite YAML.
* Developers gain intuitive self-service without risk of misconfiguring critical Kubernetes primitives.
* Complete traceability: Every active pod in production maps directly to an exact `ComponentRelease`, Git commit SHA, and approval audit log.

### 1. Enterprise OIDC Integration (Plugging in Google Workspace & Corporate IdPs)
While OpenChoreo bundles a lightweight identity provider (ThunderID) for quick local prototyping, production deployments federate directly with corporate Identity Providers (IdPs) via standard **OpenID Connect (OIDC)**.

In the OpenChoreo Control Plane Helm values (`values.yaml`), administrators configure OIDC discovery:

```yaml
security:
  authn:
    oidc:
      enabled: true
      issuer: "https://accounts.google.com"
      discoveryUrl: "https://accounts.google.com/.well-known/openid-configuration"
      clientId: "${OPENCHOREO_OIDC_CLIENT_ID}"
      # Claim mappings for subject extraction
      claims:
        username: "email"
        groups: "groups"
```

Every request sent to the OpenChoreo API server—whether originating from a developer's terminal running `occ`, the Backstage OpenChoreo backend plugin, or an autonomous agent—must present an OIDC-issued JSON Web Token (JWT). The control plane cryptographically validates the token's JWKS signature, audience, and expiration before parsing claims.

### 2. The Three-Dimensional Authorization Model: Subject ✖ Action ✖ Scope
OpenChoreo structures authorization across three explicit dimensions:

> **Authorization Decision Formula**:
> `Authorization Decision = f(Subject, Action, Scope)`

1. **Subject (Who is asking?)**: Extracted directly from validated token claims:
   * Group-level: `groups: platform-admins@company.com`
   * Squad-level: `groups: checkout-squad@company.com`
   * User-level: `email: alice@company.com`
2. **Action (What operation is attempted?)**: Structured hierarchically as `resource:verb`:
   * `clustercomponenttype:create`, `component:deploy`, `component:view`, `dataplane:admin`
3. **Scope (Where is the action valid?)**: Defines the blast radius boundary:
   * **`cluster`**: Global platform scope (infrastructure definitions, gateway topologies).
   * **`project:<name>`**: Project-level scope (specific business microservices and endpoints).
   * **`environment:<name>`**: Environment-specific boundary (e.g., permits deployment in `dev` but denies in `prod`).

### 3. Production Scenario: Platform Admin vs. Read-Only Developer

Here is how OpenChoreo enforces the exact requirement: **"Platform engineers possess administrative control, while application developers have restricted or read-only access."**

#### A. Platform Administrator Binding (`ClusterRoleBinding`)
Platform engineers require cluster-wide permissions to define Golden Paths and manage data plane gateways:

```yaml
apiVersion: openchoreo.dev/v1alpha1
kind: ClusterRoleBinding
metadata:
  name: platform-engineers-admin-binding
subjects:
  - kind: Group
    name: platform-admins@yourcompany.com
roleRef:
  kind: ClusterRole
  name: platform-admin-role
  # Grants clustercomponenttype:*, dataplane:*, project:*, component:*
```

#### B. Application Developer Scoped Binding (`ProjectRoleBinding`)
Application engineers in `checkout-squad` are restricted strictly to their domain namespace and blocked from sensitive infrastructure:

```yaml
apiVersion: openchoreo.dev/v1alpha1
kind: ProjectRoleBinding
metadata:
  name: checkout-devs-binding
  project: checkout-project
subjects:
  - kind: Group
    name: checkout-squad@yourcompany.com
roleRef:
  kind: ProjectRole
  name: developer-readonly-prod
rules:
  # In production, developers have strictly Read-Only observability
  - environments: ["prod"]
    actions:
      - "component:view"
      - "telemetry:logs:read"
      - "telemetry:metrics:read"
  # In development, developers can deploy and test new component revisions
  - environments: ["dev"]
    actions:
      - "component:create"
      - "component:update"
      - "component:deploy"
      - "telemetry:*"
```

* **The Zero-Trust Result**: If an engineer from `checkout-squad` attempts to deploy directly to the `prod` environment or alter a `ClusterComponentType` via `occ component deploy --env prod`, the OpenChoreo Control Plane evaluates the JWT claims, confirms the action is unauthorized for `prod` scope, and immediately rejects the request with an HTTP 403 Forbidden.

### 4. End-to-End Governance: Backstage + OpenChoreo Symbiosis
By integrating Chapter 11's Backstage Google SSO with Chapter 12's OpenChoreo OIDC RBAC, enterprise platform teams achieve seamless defense-in-depth:

1. **Experience Plane (Backstage)**: User logs in via Google Workspace → Backstage UI renders a clean, tailored experience, hiding administrative buttons and guiding developers along paved roads.
2. **Control Plane (OpenChoreo)**: All actions dispatched from Backstage (or CLI/MCP) pass the signed JWT to OpenChoreo → OpenChoreo independently verifies group claims against its Three-Dimensional RBAC policy.
3. **Agentic Plane (AI Agents)**: Autonomous SRE and FinOps agents authenticate using scoped service account tokens, ensuring that even fully autonomous agentic workflows remain strictly confined within their designated operational boundaries.

# Cell-Based Architecture (CBA): Architectural Governance in Practice

As microservice architectures expand to hundreds or thousands of services, organizations inevitably encounter the **"Microservice Spaghetti Trap"**: unbounded East-West network calls, untrackable cross-service cascading failures, and distributed deadlocks.

To solve this systemic hazard, OpenChoreo implements the **Cell-Based Architecture (CBA)** pattern (an architectural standard pioneered by WSO2). Within OpenChoreo, an application **`Project` serves as the physical and logical boundary of a Cell**:

```mermaid
flowchart TB
    subgraph CellBorder["Cell Boundary (Project: Checkout & Order Domain)"]
        direction TB
        
        subgraph Perimeter["Cell Perimeter Gateway (Envoy Gateway)"]
            CellGW["Cell Ingress Gateway<br/>(TLS Termination, AuthN/AuthZ, OpenAPI Validation)"]
        end
        
        subgraph InternalMesh["Cell Internal Substrate (Zero-Trust East-West via Cilium)"]
            direction LR
            OrderSvc["Order Service<br/>(REST API)"]
            PaymentSvc["Payment Service<br/>(Internal RPC)"]
            CartWorker["Cart Worker<br/>(Async Worker)"]
            OrderDB[("Project Dedicated<br/>Database / Cache")]
            
            OrderSvc --> PaymentSvc
            OrderSvc --> CartWorker
            PaymentSvc --> OrderDB
        end
        
        CellGW --> OrderSvc
    end

    ExternalTraffic["External Consumers / Web Clients"] -->|North-South Ingress| CellGW
    OtherCell["Adjacent Cell<br/>(Project: Inventory Domain)"] -->|Governed Cross-Cell Gateway Call| CellGW
```

### Architectural Rules of the OpenChoreo Cell Model

1. **North-South vs. East-West Separation**:
   * **Cell Ingress Gateway (North-South)**: Every Cell exposes its capabilities strictly via its perimeter gateway. External consumers and adjacent cells can *never* directly hit internal pod IPs or arbitrary ports.
   * **Intra-Cell Mesh (East-West)**: Inside the cell, services communicate via high-performance, zero-trust mTLS managed by Cilium and Envoy, isolated within the project's dedicated namespace.
2. **Deterministic Blast Radius Containment (≤ 15%)**:
   In accordance with the Agentic Reliability Engineering (ARE) governance framework, if an unhandled memory leak or deadlock strikes `PaymentSvc`, the incident is strictly confined inside the Cell. Circuit breakers on the perimeter gateway immediately shield external callers, preventing catastrophic cluster-wide cascade failures.
3. **Decoupled Team Ownership**:
   Each Cell corresponds cleanly to a domain squad. Squads possess full autonomy to deploy, canary-test, and update components within their cell without coordinating cluster-wide network policies.

OpenChoreo's most revolutionary dimension is its **first-class adoption of the Model Context Protocol (MCP) and autonomous AI agents** directly inside the platform engine:

## 1. SRE Autonomous Agent
When services fail (OOMKilled, CrashLoopBackOff, HTTP 504s), on-call engineers often burn hours searching disjointed tools. As demonstrated in Chapter 11 Figure 11.2, when ArgoCD and OpenChoreo detect a failing canary pod, the SRE Agent proactively pushes structured diagnosis cards directly into the Backstage developer portal.

* **Automated Awakening**: Triggered automatically upon telemetry alert anomalies.
* **Context Assembly**: Queries the OpenChoreo MCP Server to retrieve recent Git commits, configuration changes, and dependency graphs.
* **Trace Analysis**: Follows failing OpenTelemetry trace IDs to isolate exceptions.
* **Instant RCA Delivery**: Synthesizes a structured Root Cause Analysis report within seconds, identifying the offending commit and proposing concrete fixes.

## 2. FinOps Autonomous Agent
Workload owners frequently over-provision resources out of caution.

* Continuously benchmarks actual CPU and memory usage against requested values.
* Cross-references utilization against platform SLOs.
* Generates **Rightsizing** recommendations and opens automated Pull Requests against `component.yaml` to optimize infrastructure costs safely.

## 3. Portal Assistant & Native MCP Server
OpenChoreo ships with an out-of-the-box **Model Context Protocol (MCP) server**:

* Exposes all platform entities (Projects, Components, Builds, Environments) as standard **MCP Resources**.
* Packages telemetry queries and log retrieval into governed **MCP Tools**.
* **Elevating OpenAPI Specs into Dynamic AI Tools (OpenAPI-to-MCP Tooling)**: The MCP server dynamically ingests the OpenAPI schemas declared across components and converts them into governed tool definitions. When an engineer instructs the assistant, "*Issue a test authorization to payment-service to verify the new gateway route*", the agent inspects the OpenAPI schema, constructs a valid payload, and executes the call against the sandbox environment safely.
* Developers converse naturally with the Backstage Portal Assistant ("*Show me error logs for payment-service in Prod over the last 30 minutes*"), grounded in verified, real-time platform data without hallucination.

# Hands-On Walkthrough: Running OpenChoreo Locally

## 1. Prerequisites
* **Docker**: Installed and running.
* **Kubectl**: Configured.
* **Kind**: Kubernetes in Docker.

## 2. Install the `occ` CLI
```bash
curl -fsSL https://openchoreo.dev/install.sh | bash
occ version
```

## 3. Create a Local Cluster
```bash
occ cluster create --wait
```
This deploys the OpenChoreo Control Plane, Envoy Gateway, and core CRDs onto a local Kind cluster.

## 4. Deploy Your First Service
```bash
# Create a project namespace
occ project create demo-project

# Deploy a component using the sample repository
occ component create hello-service \
  --project demo-project \
  --type microservice-rest \
  --git-repo https://github.com/openchoreo/sample-apps \
  --git-branch main \
  --context-dir ./hello-world \
  --port 8080
```

## 5. Verify Reconciliation and Test Endpoints
```bash
occ component status hello-service --project demo-project
```
In seconds, OpenChoreo builds the image, creates Envoy HTTPRoutes, and brings the service live.

Test the endpoint:
```bash
curl http://localhost:8080/hello
```
Response:
```json
{
  "message": "Hello from OpenChoreo Cloud-Native IDP!",
  "status": "healthy"
}
```
