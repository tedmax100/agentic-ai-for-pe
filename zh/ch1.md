# 1

# 平台工程與開發者體驗

你是否曾覺得，要將自己的程式碼部署到正式環境（Production），簡直就像在走一座複雜的迷宮？你只想全心打造優質的功能，但卻被迫花費大量時間與基礎設施搏鬥、解讀晦澀難懂的錯誤訊息，並試圖將十幾種互不相通的工具拼湊在一起。我們深切體會過這種痛苦。我們見過無數團隊耗費大把寶貴的時間，不是在打造出色的產品，而是在與底層系統的複雜性苦苦糾纏。

多年來，我們在軟體開發歷程中始終在與這種複雜性對抗。當我們從低階組合語言走向高階程式語言時，我們慶祝；當我們告別實體伺服器擁抱雲端時，我們再次慶祝。每一步——就像 DevOps 一樣——都是試圖在技術泥沼之上架起一座更高的橋樑，旨在減輕開發者的心智負擔並加速創新。平台工程（Platform Engineering）正是這場追尋中的下一個自然進程。我們曾以為，只要為開發者提供所需的一切自助服務工具，就能為他們鋪出一條平坦順暢的「鋪好之路」（Paved Road）。然而，我們很快發現，我們並沒有真正消除複雜性，只是將複雜性轉移了位置。如今，開發者面臨著一種新型態的困惑，而我們——平台團隊本身——則發現自己必須負責打造與維護這個極其複雜的內部產品。這聽起來是否很熟悉？

本章要探討的是下一次飛躍，我們相信這項技術將最終幫助我們馴服這頭巨獸：**AI 驅動的平台工程（AI-driven Platform Engineering）**。我們將直面那些仍在困擾我們的棘手難題：我們該如何減輕開發者沉重的認知負擔？我們該如何證明內部平台不僅僅是成本中心，而是創造商業價值的強大引擎？我們又該如何真正將內部平台視為一款正式產品，並為值得享有優質體驗的真實使用者（內部開發者）提供服務？

我們的目標是向你展示人工智慧（從智慧自動化到實用的 AI 代理 Agent）如何顛覆這一切。我們將深入探討 AI 如何協助我們將平台工程從一個被動「救火」的支援團隊，轉變為主動出擊、具備自我改進能力的引擎，從而大幅提升開發者生產力並增強企業敏捷度。我們所討論的不僅僅是任務自動化。我們將展示 AI 如何賦予內部平台自主管理複雜性的智慧、預測開發者的下一步需求，並打造近乎毫不費力的極致開發者體驗。

在本章中，我們將深入剖析：

* **開發者面臨的真實生產力挑戰**，以及如何透過結合 Kubernetes Operator 與基礎設施即程式碼（IaC）等工具的自助服務平台，作為解決這些問題的第一步。
* **如何衡量真正關鍵的指標**。我們將超越單純的監控數據，深入探討 SRE、DORA 指標、SLO、SLA 與 SLI，將平台表現與真正的業務目標（例如使用者滿意度與營收增長）緊密連結。
* **如何跳脫自動化思維，將平台視為一項產品（Platform as a Product）**。這是一次思維模式的轉變。我們將探討如何運用產品管理思維打造深受開發者喜愛的平台，並制定明確且以價值為導向的未來發展藍圖。

# DevOps 演進為 AI 驅動的平台工程

想像一下，一位開發者花了數小時除錯記憶體洩漏，或是手動配置伺服器，他們的創造力完全被繁瑣的基礎設施任務所扼殺。在我們的技術生涯中，隨著業界不斷引入「抽象化」（Abstraction）來降低認知負擔，我們見證了這場掙扎的演進歷程。從低階程式碼到雲端編排，這些進步為平台工程奠定了基礎——平台工程是一門將維運複雜性自動化的專業領域，旨在賦能開發者專注於創新並交付商業價值。

開發者該如何應對現代軟體系統日益增長的複雜度？就像汽車與飛機透過大幅提升速度與效率徹底改變了交通旅行一樣，軟體技術也透過簡化開發流程的抽象化持續演進。從 Python、Java 等高階語言，到 React 與微服務架構，再到容器化與 Kubernetes 等工具，軟體應用的部署與編排變得更加順暢。這些推動創新的*載具*讓開發者能以更少的心力建構複雜系統，不僅提升了生產力，也縮短了產品上市時間（Time-to-Market）。

然而，像 Kubernetes 這樣的工具也引入了「熵」（Entropy，即來自多樣化配置選項所帶來的複雜性），若未妥善管理，將給開發者帶來巨大挑戰。如今，AI 驅動的平台正透過智慧化自動化與最佳化工作流程來解決這一難題。

這種抽象化歷程最終導向了平台工程——這是 DevOps 的自然演進，讓開發者能夠專注於解決核心業務問題並交付商業價值，我們接下來將對此進行探討。

## 平台工程的興起

平台工程將抽象化原則推向了全新高度，其核心焦點在於優化開發者體驗（Developer Experience, DevEx）並實現維運任務自動化。這反映出業界愈發重視成立專屬團隊，致力於支援開發者快速且高效率地建構與部署軟體。平台工程所提供的核心抽象，就是透過自動化提升開發者體驗。開發者過去必須透過開立工單（Ticket）來申請建立 Git 儲存庫、配置雲端資源或建置 CI/CD 管線的日子已經一去不復返。取而代之的是，這些維運任務都透過自助服務平台（Self-Service Platform）自動完成。這些平台內建安全與治理防護欄（Guardrails，例如自動化合規檢查），並統一管理雲端資源配置。開發者不再需要把寶貴時間浪費在這些繁瑣且容易出錯的工作上，而是能專注於他們最擅長的事：撰寫程式碼與打造創新的解決方案。平台工程的終極目標是消除維運層面的認知負擔。平台團隊扮演著內部服務供應商的角色，提供預先建構好的基礎架構、服務與工具，讓開發者能輕鬆且迅速地部署應用程式。

我們仍清楚記得，過去設定一套開發環境可能需要數天甚至數週的時間。這包括配置伺服器、安裝軟體與管理依賴項，過程耗時、容易出錯且往往令人無比沮喪。如今，透過落實良好的平台工程實踐，幾分鐘內即可大功告成。藉助**基礎設施即程式碼**（**IaC**）、容器化與自動化部署管線等工具，平台團隊可以建立標準化且可重複利用的環境，隨時快速啟動。這種轉變對開發者的生產力與滿意度產生了革命性的影響。然而，儘管自助服務能力解決了早期手動工單申請的瓶頸，卻也帶來了全新的挑戰：如何管理這些內部平台自身日益增長的複雜性。這正是 AI 作為下一層不可或缺的抽象化層次登場的契機，它將我們的內部平台從靜態工具升級為更具智慧的系統。

透過將開發者從維運複雜度的重擔中解脫出來，平台工程使他們能夠更具生產力、更有創造力，並全神貫注於為企業創造價值。

這種轉變不僅僅是為了追求便利，更是為了加速創新並推動企業敏捷性。放眼未來，我們正見證「*平台之平台*」（Platforms of Platforms）的崛起，它們在現代軟體版圖中為開發者全面賦能。這項重大變革象徵著軟體開發環境正邁向更具彈性的架構。這些元平台（Meta-platforms）在平台工程層內暴露 API，從而促成更高層次的抽象化。這種架構演進帶來了更高的客製化彈性、效率與可擴展性，也凸顯了平台工程在串聯孤島系統與簡化工作流程方面的關鍵定位。

在擁抱這套方法的頂尖高效能組織中，其優勢顯而易見，這表明平台工程不僅能提升效率，還能直接帶動整體業務成果的提升。然而，這一趨勢並非僅關乎技術，它是一種涵蓋人員與流程的整體性方法。正如《*鳳凰專案*》（*The Phoenix Project*）共同作者 Gene Kim 常說的：「*改善日常工作，甚至比做好日常工作本身更為重要。*」平台工程透過持續改善開發者的日常工作體驗，完美體現了這一原則。透過專注於自動化、自助服務能力與流暢的工作流程，平台團隊致力於消除摩擦力，讓開發者更具生產力且更加專注。這項哲學超越了單純的工具層面，深入探討人性維度，將開發者的滿意度與工作成效置於首位。

在我們看來，從打孔卡到平台工程的軌跡，不僅代表了技術上的躍進，更代表著軟體開發思維的根本變革。其核心在於賦能開發者專注於他們最擅長的事：為現實世界的問題打造創新的解決方案。透過將基礎設施與維運的繁雜細節抽象化，我們為軟體開發的創造力與創新開拓了全新的可能性。這種轉變將帶來更快的開發週期、更具敏捷度的團隊，以及更迅速向客戶交付價值的能力。軟體開發的未來，正與平台工程的持續演進以及形塑下一代數位創新的「*平台之平台*」緊密相連。

## 現況發展：AI 驅動的平台

在撰寫本書之際，我們正親身經歷平台工程的一場深刻變革，這場變革正由 AI 引領，特別是能夠自主最佳化系統的代理式 AI（Agentic AI）。我們之前討論過的傳統平台工程方法正在快速進化，我們在建構、維護平台以及與之互動的方式上，正經歷著巨大的轉變。

將 AI 整合至平台工程早已遠遠超越了單純的自動化範疇。現在的核心在於在開發者與基礎設施之間建立智慧化的對話介面。正如早期的抽象化層會在系統中引發新型態的「熵」（複雜性）一樣，AI 同樣帶來了自身的複雜度。然而，與以往的技術進步截然不同的是，AI 系統能夠透過自我最佳化與自主故障排除，積極主動地協助管理這些熵。

延續前文探討的「平台之平台」概念，**大型語言模型**（**LLMs**）與平台工程的整合，在很大程度上得益於**模型上下文協議**（**Model Context Protocol, MCP**）的推動。MCP 伺服器本身並不直接建立整合，而是為 LLM 提供了一種與各類平台 API 進行互動的標準化方式。這使得 LLM 能夠充當智慧層，理解上下文、過往互動記錄與複雜需求，並能將人類意圖精準轉化為橫跨多個平台服務的具體技術實作。舉例來說，開發者可以使用自然語言發出建立新微服務的請求。或者，LLM 可以透過 MCP 關聯多個微服務的日誌、分析 Git 中近期的配置變更，診斷部署失敗的原因並主動提出修復補丁（Patch）。這種基於 API 的架構讓企業能夠將平台功能以工具的形式開放給 LLM，建構起更具彈性與擴充性的生態系。這項進展象徵著朝向更直覺、更高效的平台管理邁出了關鍵一步，多個底層系統的複雜性得以透過具備上下文感知的智慧介面完美抽象化。

代理式 AI（Agentic AI）的崛起重新定義了平台工程的格局。AI 不再只是一個輔助工具，而是成為平台工程生態系中的積極參與者。這些代理式 AI 系統能夠主動預判潛在問題、提出最佳化建議，甚至在獲得核准後自主實施變更。AI 驅動的平台工程潛力遠超乎一般的維運效率提升。我們目前正在探索與構建所謂的**認知平台（Cognitive Platforms）**——這類系統不僅能從使用者行為中學習並自動調整其配置，更能預測未來需求並主動自我演進。這些平台能預測資源需求、即時最佳化成本，甚至根據對使用模式與效能指標的深度分析提出架構改進建議。

在平台工程領域中，安全性與合規性因 AI 的加入而同時迎來了革命與挑戰。一方面，先進的 AI 系統大幅增強了我們持續監控安全態勢的能力，能根據新型威脅自動更新安全策略，甚至模擬潛在的攻擊場景以主動佈防。隨著圍繞 AI 與雲端運算的法規架構快速演進，這種預測性安全防禦方法變得至關重要。另一方面，AI 的整合也帶來了新的安全隱憂。賦予 AI 過高存取權限的風險，再加上其自主決策能力以及自我修改行為的理論風險，為我們平台的安全防護帶來了全新挑戰。

將 AI 整合到平台工程雖然具有變革性，但也並非沒有複雜難題。有關 AI 治理、AI 決策的可靠性以及人類監督（Human-in-the-loop）的必要性，依然是社群中熱烈討論的焦點。賦予 AI 高效管理複雜性能力的同時，如果沒有妥善的控制機制，也同樣會引發它可能引入新型風險的擔憂。然而，正如先前的每個抽象層都帶來了相應的熵一樣，AI 代表了一個獨特的歷史轉折點：這是一項不僅能製造複雜性，還具備自主管理複雜性能力的新技術，前提是我們必須落實正確的防護欄與治理架構。

從打孔卡到 AI 驅動平台工程的轉變，不僅彰顯了技術的進步，更標誌著團隊共同創造、維運與創新方式的徹底革新。透過不僅將基礎設施與維運的複雜性抽象化，更將決策制定與系統最佳化的繁瑣細節抽象化，我們正在為軟體開發與維運開拓出嶄新的可能性。

展望未來，平台工程與 AI 之間的協同效應無疑將持續深化。透過像 MCP 這樣的標準化協議，認知平台正逐漸成為現實，使大型語言模型能夠與我們的工具和系統無縫互動。我們正在邁向一個平台不僅僅負責隱藏複雜性，而是主動進行自我最佳化與持續演進的全新世界，這將帶來我們如今才剛開始想像的高效率、高可靠性與創新浪潮。

# 開發者生產力挑戰與自助服務能力

正如我們在前一節所探討的，從 DevOps 到平台工程的演進歷程，始終是由抽象化複雜性與減輕開發者認知負擔的需求所驅動。然而，這段歷程並非一帆風順。那些旨在簡化開發者生活的技術進步，在某些情況下反而帶來了全新的複雜性與職責負擔。在我們探討 AI 如何改變這個領域之前，先釐清當前開發者所面臨的挑戰，以及自助服務能力在應對這些挑戰中所扮演的角色，將非常有助於我們全面理解問題的全貌。

儘管我們竭盡所能想要簡化開發者的工作，他們仍面臨著多重挑戰，這些挑戰持續造成顯著的認知負擔。現代開發者必須應對龐雜繁多的職責：從管理複雜的基礎設施、熟悉不斷膨脹的工具鏈，到確保安全合規性以及最佳化系統效能。他們發現自己必須在編寫程式碼、除錯、部署與維運任務之間頻繁切換工作情境（Context Switching），這極大地打擊了他們的生產力與專注度。花在基礎設施和服務配置上的時間，往往壓過了專注於開發核心業務邏輯的時間，導致挫折感加劇且效率低下。技術與方法的迅猛更迭進一步加劇了這些挑戰，形成了永無止境的學習曲線，這既令人興奮，同時也令人筋疲力竭。

## 自動化與自助服務的興起

這段歷程始於一群 DevOps 先驅者意識到了這些痛點。他們開始撰寫自動化腳本來配置資料庫、虛擬機器與雲端服務（如 Kubernetes 叢集、API 閘道與事件匯流排等資源）。他們的目標既簡單又宏大：在維持安全參數與架構規範的同時，將所有環節全面自動化。

隨著越來越多團隊採用 Terraform，基礎設施即程式碼（IaC）運動迅速蔚為風潮。這種方法允許開發者用程式碼來定義與管理基礎架構，進而實現版本控制、協同作業與高度可重複性。然而，這套解決方案也帶來了自身的一系列新問題。

雖然自動化腳本和 IaC 解決了環境的可重複性問題，但它們引發了新的難題：如何以「自助服務」的方式讓廣大開發者輕鬆取用這些能力？早期的嘗試通常依賴既有工具，例如使用 Jenkins 執行任務、使用 Rundeck 進行流程自動化。團隊會打造 Web 介面或命令列工具（CLI）來觸發這些自動化流程，但這些方案往往四分五裂且難以長期維護。每個團隊可能都會打造專屬的工具與介面，導致整個企業內部充斥著大同小異卻互不相容的重複解決方案。這種碎片化讓業界產生了一個關鍵頓悟：基礎設施自動化必須被視為一項「產品」，而不僅僅是零散腳本的集合。企業開始明白，提供自助服務能力需要與任何軟體產品一樣，給予相同水準的使用者體驗、說明文件與支援服務。這種從「將平台視為專案」到「將平台視為產品」的思維轉變，為後續更成熟的解決方案奠定了基石。

## 內部開發者平台（IDP）的誕生

朝向開發者自主權的轉變並非始於現代的開發者入口網站（Developer Portals）。早在 Backstage 出現之前，像 Cloud Foundry 這類的平台就已經開創了自助式基礎設施的先河。當時的開發者經常受到阻礙，四處尋找對口的人員、正確的腳本或相應的說明文件。這令人沮喪，並且拖慢了所有進程。隨後，新型態的開發者入口網站應運而生，宛如熱帶雨林中央繁華的城市廣場。頓時之間，大家有了一個統一的去處。憑藉友善的介面、清晰的範本與自動化工作流程，開發者獲得了指引方向的地圖與指南針。他們終於可以專注於打造應用，而不是與周遭惡劣的環境搏鬥。這不僅僅是一個新工具，而是一次深刻的觀念蛻變。我們開始不再把內部平台視為腳本與伺服器的堆疊，而是將其當作一款產品，並將內部開發者視為備受尊重的尊貴客戶。

但旅程並未就此結束。雖然這個「城市廣場」非常出色，但管理背後複雜的雲端機械運作仍像是一門門檻極高、純技術性的工作。這就像為汽車配備了一個精美簡單的數位儀表板，但每次想要增加新功能時，你依然必須具備專業修車技師的技能。我們該如何將這種複雜性融入開發者早已熟悉的世界中呢？

這正是下一場革命的起點——**Kubernetes Operator** 的興起。我們見證了強大工具的相繼問世，包括用於打包應用程式的 **Helm**，以及用於管理基礎設施的 **Crossplane**、**Kube Resource Orchestrator**（**kro**）和 **AWS Controllers for Kubernetes**（**ACK**）。這些不僅僅是工具，更是「翻譯官」。它們教會了 Kubernetes 直接說雲端供應商的原生語言。剎那間，資料庫、訊息佇列或儲存貯體不再是必須透過另一個雲端主控台手動配置的外在資源，而是轉變成可以直接從 Kubernetes 叢集內部請求的原生資源。透過轉向這種集中式、宣告式的模型，我們建立了一個超越純粹基礎設施配置的單一信任來源（Single Source of Truth）。這使我們能夠將零散的工作流程（如 CI/CD 管線與安全策略強制執行）直接整合成平台的核心底座。這從根本上簡化了系統架構引擎，更重要的是，大幅降低了平台團隊自身的認知負擔。透過讓系統自主處理這些模式，我們將干擾從平台工程師身邊引開，使他們不再淪為「開單接單員」，而是能專注於高價值架構設計。對於開發者來說，這是一場劃時代的變革；我們不僅給了他們一個更漂亮的儀表板，更從根本上簡化了他們賴以生存的底層引擎。*圖 1.1* 展示了 Kubernetes 控制平面如何集中管理基礎架構並整合零散的管線：

## 認知負擔的重新分配

然而，必須深刻體會的一點是：這場演進並未消除複雜性，而是「重新分配」了複雜性。在過去，維護這些強大抽象層的重擔完全落在了平台團隊身上。他們既要對底層基礎設施有著深入透徹的理解，又必須細緻洞察開發者的微觀需求。雖然這項工作對於實現商業價值至關重要，但它往往讓平台工程師深陷於工單海洋、疑難排解與手動介入的泥淖中，產生持續而沉重的認知負擔，扼殺了他們自身的創新潛能。

將人工智慧與機器學習引入該領域，終於開始改變這種失衡的動態。我們正從「單純為開發者抽象化基礎設施」，跨越到「利用 AI 作為平台團隊本身的戰力放大器」。隨著這些技術日益成熟，它們提供了一條將那些無休止、令人分心的「機械性」繁瑣工作從人類工程師轉移給智慧型自動化系統的途徑。想像一下，AI 系統不僅能自動配置資源，還能在人類察覺問題之前，主動偵測並修復基礎設施隱患、預測容量擴展需求並調校系統效能。透過接管平台的「日常庶務」，AI 將平台工程師從工單處理員的角色中解放出來，使他們能夠全心投入高層次的系統架構設計與生態系的戰略演進。

縱觀這段歷程，每一次演進都讓我們更接近一種可持續的平衡狀態。從手動腳本到自助服務平台，再到 Kubernetes Operator，我們一直在為這下一個階段打下地基。找到適當的平衡點依然至關重要：我們既致力於簡化開發者的日常工作，同時也竭力守護平台團隊的專注力以及整體系統的安全穩固。所謂的效率，核心在於確保我們的技術基礎設施與寶貴的人才資源都能得到最高價值的發揮。

展望未來，具備成熟標準化規範與明確職責劃分的組織，將最有能力充分發揮 AI 的威力。AI 的角色將是編排與增強現有流程，扮演終極的「平台智慧助理」。舉例來說，在 GitOps 工作流程中，AI 可以透過 Pull Request 主動提出設定檔變更建議，但實際的執行與治理依然牢牢錨定在控制器中，嚴格遵循平台團隊所規範的標準模式。

這場旅程不僅僅關乎引進新工具，更在於深入理解整個研發團隊持續演變的真實需求。引領趨勢的組織將能巧妙融合標準化、清晰的職責劃分與人工智慧，打造出真正能全面賦能的生態系，讓開發者與平台工程師都不再感到不堪重負。當我們進入指標討論時，我們將探討不同組織如何因應這些挑戰，以及我們能從他們的經驗中汲取哪些智慧。我們將看到企業如何策略性地運用指標，不僅僅衡量交付速度，更用以推動技術創新、最佳化內部開發者體驗，並確保技術舉措與商業目標以及建構系統的團隊身心健康緊密對齊。

# 以 SRE、MTTR、DORA 指標、SLO、SLA 與 SLI 衡量成效

在深入探討了平台工程的演進歷程並剖析了開發者生產力挑戰之後，我們來到了一個關鍵問題：*我們究竟該如何衡量平台各項舉措的成功？*

答案在於「指標」，但挑選並落實合適的度量標準，遠沒有表面上看起來那麼簡單直觀。多年來，我們在生活中的幾乎每一個層面都受到各類指標的引導。從小時候開始，父母就鼓勵我們要考出好成績並專注於學業，這讓我們很早就體會到數字與基準是如何形塑我們前進的道路。我們並非認為這有何不妥，但我們往往會忽略讀書學習的核心初衷：獲取知識並為未來的職業生涯成就做好準備。

在我們的職場生涯中，我們也經常掉入濫用指標的陷阱。我們往往將目光死死釘在諸如降低成本、減少事故數量、提升 SLA 達標率以及守住錯誤預算（Error Budget）等數字目標上。

問題在於，被這些數字所考核的同仁往往達成了目標，卻根本不明白背後真正的商業理由。他們可能並未意識到最終的目標其實是：

* 更快地為使用者交付全新功能
* 在關鍵銷售活動期間確保服務穩定可用
* 將維運干擾從平台工程師轉移至智慧系統
* 減輕整個研發組織日常的認知負擔

這就像一個團隊可能會安裝一套完整的 Prometheus 可觀測性技術棧，自帶數十個預先建好的儀表板，但實際日常卻只會查看與其核心服務息息相關的少數幾個指標。

歸根結底，缺乏明確商業導向意圖的盲目指標追蹤，是毫無意義的。我們冒著全力追逐那些對業務成功根本無關緊要的數字的巨大風險。

從技術指標的視角來看，商業成功是一個超越傳統財務指標的多元概念。它涉及維運效率、客戶滿意度、創新能力與長期永續性之間的細緻平衡。在數位時代，技術已經成為絕大多數企業運作的骨幹，這使得技術表現與整體商業目標保持一致變得生死攸關。

真正的成功衡量標準，在於組織能否有效發揮其技術實力來推動業務成長、提升客戶體驗並在市場中維持競爭優勢。這需要採取全盤性的方法來挑選與分析指標，確保每一項技術指標都能直接與具體的業務成果掛鉤。例如，系統正常運行時間（Uptime）不僅僅是維持一個漂亮的高百分比數字，更是為了確保穩健一致的服務交付，從而轉化為客戶的信任度與品牌忠誠度。

在這種背景下，成功也絕非一成不變。隨著企業演進與客戶期望的轉變，定義成功的指標也必須與時俱進。這種動態特質要求我們持續重新評估成功的構成要素以及衡量方式。組織經常會發現，過去曾象徵成功的指標隨著時間推移可能會變得不再那麼關鍵，因而需要導入全新、更切合現況的指標。

最終，企業在技術指標層面的成功，應當取決於這些指標能否精準反映公司達成戰略目標、滿足客戶需求與驅動創新的能力。這意味著我們必須看透表面的技術表現，深入理解其對業務運作、市場地位以及未來成長潛力的深遠影響。

## 將技術指標連結至商業成功

以下是企業常用於結合技術指標來衡量成功的七大關鍵指標：

* 用於衡量使用者體驗的**客戶滿意度評分**（**CSAT**）或**淨推薦值**（**NPS**）
* 用於衡量營收效益的**每使用者營收**（**RPU**）或**每使用者平均營收**（**ARPU**）
* 用於衡量產品採用率的**使用者活躍度**（例如：每日活躍使用者 DAU / 每月活躍使用者 MAU）
* 用於衡量系統可用性的**系統可靠性**（例如：正常運行時間百分比、錯誤率）
* 新功能的**上市時間**（Time to Market）
* 用於衡量成本節約的**成本效益**（例如：每位使用者的基礎架構成本）
* 用於衡量業務成長的**創新指數**（例如：來自新產品/新功能的營收佔比）

讓我們設想一家虛構的跨國電商公司 *TechShop Global*，該公司曾面臨數位平台效能上的嚴峻挑戰。面對數百萬的日活躍訪客以及龐雜的商品目錄，他們迫切需要徹底革新平台可靠性與使用者體驗指標的衡量與管理方法。

該公司藉由採用 AWS 雲端服務落實全面的雲端原生架構，開啟了他們的轉型之旅。他們利用 Amazon EKS 進行容器編排，並使用 EventBridge 與 SQS 建構事件驅動架構。這項戰略舉措帶來了令人驚豔的成效：部署時間從過去的 30 天大幅縮短至僅需 5 分鐘，達到了金融領域常見的卓越標竿水準。

他們的數據分析揭示了一項極其關鍵的洞察：商品頁面載入每延遲 2.3 秒，就會導致轉換率驟降 40%。這項發現深刻印證了技術效能與商業成果之間密不可分的關聯。

透過詳盡的使用者行為分析，他們進一步發現：在單次購物過程中遭遇 3 次或以上搜尋失敗的客戶，在接下來一週內回訪的機率降低了 65%。這項指標隨即成為推動後續技術改進的核心動力。

為了解決這些挑戰，TechShop Global 推行了多項創新解決方案：

* 利用 AWS 整合服務打造精細的高效快取策略
* 引進以 AI 驅動的預測性自動調整容量機制（Predictive Scaling）
* 打造客製化的平台工程解決方案以最佳化運算工作負載

這項轉型帶來的商業效益極為顯著：

* 在 6 個月內使客戶帶來的營收提升了 46%
* 維運成本降低了 50%
* 平台可靠性從 99.90% 提升至 99.99%
* 新功能的上市時間從 6 個月大幅縮減至 7 週

此外，TechShop Global 在三個關鍵領域取得了突破性改善：

* **客戶滿意度評分**（**CSAT**）：CSAT 分數從 3.8 分躍升至 4.7 分（滿分 5 分），充分體現了使用者體驗與平台可靠性的大幅提升。
* **使用者活躍度**：每日活躍使用者與每月活躍使用者的比例（DAU/MAU）從 0.3 提升至 0.5，代表平台的常態使用黏著度顯著增長。
* **創新指數**：過去一年推出的新產品與新功能所貢獻的營收佔比從 15% 上升至 28%，證明該公司在創新推廣與新產品市場化能力上的飛躍。

這個案例充分證明，當現代雲端架構與平台工程得到妥善落實時，能夠同時重塑技術指標與業務成果。各項成功數據表明，專注於平台效能、使用者體驗、客戶滿意度、互動黏著度與持續創新，與企業營收增長及客戶滿意度有著直接的正相關。接下來，讓我們深入平台工程指標的世界，了解它們如何形塑現代企業的商業成功。

## 平台工程的核心指標

見證了這些指標的演變歷程，我們可以確定地說，多年來它們已經變得越來越成熟，並且更加聚焦於商業成果。

平台工程指標已經從單純的系統運行時間測量，大幅演進為反映業務健康狀況的綜合指標。在現今的技術架構中，最為關鍵的指標包括：

* 部署頻率（Deployment Frequency）
* 變更前置時間（Lead Time for Changes）
* 平均復原時間（Mean Time to Recovery, MTTR）
* 平台採用率（Platform Adoption Rate）
* 變更失敗率（Change Failure Rate）
* 基礎設施配置時間（Infrastructure Provisioning Time）
* 開發者滿意度評分（Developer Satisfaction Score, DSAT）

現在，讓我們分享許多平台團隊經常忽略的一點：錯誤預算（Error Budgets）與服務水準目標（Service Level Objectives, SLO）的關鍵價值。根據我們與各類組織合作的實務經驗，深刻理解這些概念能夠極大地改善團隊的運作模式。以錯誤預算為例，它提供了一種科學化的方法來在創新速度與系統穩定性之間取得平衡。

談到可靠性指標，讓我們先釐清三個不可或缺的核心要素：

* 服務水準協定（Service Level Agreement, SLA）
* 服務水準目標（Service Level Objective, SLO）
* 服務水準指標（Service Level Indicator, SLI）

圖 1.2：錯誤預算對比服務水準目標（SLO）

SLA 代表我們向客戶作出的正式承諾，而 SLO 則是我們的內部目標，其標準通常應該比 SLA 更加嚴格。SLI 則是我們用來追蹤實際表現的量測數據。由 DevOps 研究與評估團隊提出的 DORA 指標，則能幫助我們全面洞察軟體交付的效能水平。

技術維運指標尤其值得重點關注。**平均復原時間**（**MTTR**）衡量我們在發生故障時迅速恢復服務的速度。**復原時間目標**（**RTO**）與**復原點目標**（**RPO**）則協助我們規劃災難復原計畫以確保業務連續性。特別引人深思的是，這些指標如何與**業務影響分析**（**BIA**）相互結合，進而構建起對系統韌性的全方位深刻理解。

當涉及開發者體驗（DevEx）指標時，我們需要同時兼顧定量與定性兩個維度的評估。首次部署前置時間、平台採用率與自助服務成功率提供了客觀的量化硬數據；而開發者滿意度調查與意見回饋訪談則能為我們帶來不可或缺的定性深度洞察。

我們觀察到，卓越成功的組織往往傾向於採用平衡計分卡（Balanced Scorecard）的方法。他們將部署頻率和錯誤率等技術指標，與功能採用率和營收影響等業務指標緊密結合。這種全盤性的策略確保了平台工程的各項投入能夠直接為商業成功添磚加瓦。在具體落實時，在展開任何改進措施前先建立基準測量（Baseline）至關重要。舉例來說，在衡量 MTTR 時，應先從追蹤當前的復原時間著手，進而設定務實可行的改善目標。

最後，讓我們探討平台工程指標的未來前景。隨著系統架構日趨複雜且高度分散，新型態的指標正應運而生。全鏈路可觀測性（Observability）、使用者歷程追蹤（User Journey Tracking）以及 AI 輔助的效能最佳化正變得愈加舉足輕重。但請牢記：關鍵永遠在於將這些技術度量指標緊密錨定回商業價值之上。

# 超越自動化：將平台視為產品

平台工程的演變將我們帶到了一個技術與產品思維交會的迷人十字路口。在探討了從 DevOps 到平台工程的演進歷程、開發者生產力挑戰以及成功度量指標之後，我們現在可以進一步探討：將內部平台視為產品（Platform as a Product），將如何徹底改變它對企業組織所產生的深遠影響。

現代平台團隊越來越多地採用產品管理方法論，逐步揮別過去傳統以專案為導向的運作模式。這種轉變代表著我們看待內部開發者平台思維方式的根本性變革。根據《*平台工程現況報告（第 3 卷）*》，將平台視為產品的組織正在收穫可衡量的顯著成效：22.13% 的受訪組織回報關鍵指標獲得大幅改善，31.97% 觀察到在部署頻率與上市時間等領域有明顯進步。然而，衡量成效依然是一大挑戰——有高達 44.67% 的組織完全未追蹤任何指標，這表明在如何評估與展現平台成功價值方面，仍存在巨大的成熟度成長空間。

平台團隊中**產品負責人**（**Product Owners, PO**）的角色變得愈發不可或缺。這些 PO 必須如同面向外部客戶的產品經理一樣，精準平衡技術架構需求與內部使用者痛點。他們與平台工程師並肩緊密協作，確保開發出的平台功能能夠精準契合開發者的日常工作流程與組織的長遠策略目標。

*圖 1.3* 描繪了這個持續運轉的產品生命週期：從建構與部署平台功能，到收集開發者回饋並持續提煉產品路線藍圖。

![](./imgs/B34160_1_3.png)


圖 1.3：將平台視為產品（Platform as a Product）

在實務落實方面，成功的平台產品仰賴清晰的說明文件、直覺易用的操作介面以及穩健的技術支援體系。像 GitHub 與 GitLab 這樣的頂尖企業在這方面樹立了卓越標竿，他們的平台已成為開發者體驗的黃金典範。他們的成功雄辯地證明：以對待外部商業產品同等的匠心來雕琢內部工具，能夠帶來更高的平台採用率與更優秀的業務成效。

當我們把平台視為產品時，前文所討論的各項指標就顯得更為至關重要。客戶滿意度分數、功能上市時間與平台採用率，將直接作為指導產品方向決策的關鍵績效指標（KPI）。這種數據驅動的思維模式有助於平台團隊排定優先順序，集中資源打造能夠為內部開發者客戶創造最高價值的核心功能。

我們早先提及的安全與合規性，在這種以產品為中心的思維架構下也展現出全新維度。平台團隊必須在極致的使用者體驗與嚴格的組織安全要求之間取得完美平衡，建立起「既能提供嚴密防護又不會阻礙開發速度」的安全防護欄（Guardrails）。我們討論過的自助服務能力也成為平台產品的核心亮點，需要持續進行深度的體驗設計與反覆運算改進。

展望未來，人工智慧與自然語言處理的深度整合，正在徹底顛覆開發者與平台系統之間的互動模式。這場演進代表著平台工程的下一個璀璨前沿：在不久的將來，複雜無比的底層操作將只需透過簡單、口語化的自然語言指令即可輕鬆搞定。

平台團隊目前正在積極試驗各類由 AI 驅動的智慧助手，涵蓋從程式碼審查（Code Review）到基礎設施自動配置的各個環節。這些智慧工具具備上下文感知能力，並能根據歷史數據與業界最佳實踐主動推薦最佳配置方案。AI 重塑平台工程的潛力不可限量，我們將在後續章節中對此展開深度剖析。從*[第 4 章](https://learning.oreilly.com/library/view/agentic-ai-for/9781806386659/Chapter_4.xhtml#h1_79)*開始，每個實戰章節都配備了可親自運行的完整程式碼範例，發布於本書的專屬配套 GitHub 儲存庫：[https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering](https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering)。

平台工程的未來，在於打造以使用者為中心、能隨著使用者需求智慧演進的智慧型產品。

正如我們在與眾多企業合作過程中所觀察到的，最卓越成功的平台，永遠是那些能與使用者保持強大回饋閉環，並能敏銳因應需求變化持續演進的系統。

在踐行「將平台視為產品」的過程中，高層管理者的支持（Management Buy-in）變得生死攸關。企業組織必須深刻體認到：平台與任何對外商業產品一樣，都需要持續的資源投入與長期演進。平台工程中的產品思維絕非僅關乎工具與功能特性的堆砌，它的真諦在於建構一個在恪守企業規範的同時、能全方位賦能開發者的活力生態系。事實證明，這種架構方法具有顛覆性的變革力量，能為平台團隊及其服務的廣大開發者帶來雙贏的卓越成效。

在我們的跨組織輔導實踐中，轉向「將平台視為產品」標誌著我們在賦能開發者這條道路上的關鍵跨越。隨著技術持續向前發展，人工智慧與自然語言對話介面的深度融入將進一步昇華這一理念，使平台變得比以往任何時刻都更易取用、更加強大。

# 本章摘要

從 DevOps 演進至 AI 驅動的平台工程，不僅僅是一次單純的技術躍遷，更是我們看待軟體開發思維方式的根本性變革。我們一路走來，告別了過去手動配置伺服器那種既耗時又容易出錯的苦澀掙扎，昂首邁入了一個以智慧宣告式系統作為全組織戰力放大器的嶄新紀元。透過將內部平台視為正式產品，並全面邁向集中化、智慧化的系統編排，我們終於得以正面化解長期困擾開發者生產力的核心難題。

最關鍵的是，這段歷程讓我們深刻體認到：複雜性絕不能被簡單忽視，而必須被妥善管理。透過將 AI 不僅僅用於抽象化底層基礎設施，更將其作為維運維護的智慧合作夥伴，我們成功重新分配了認知負擔，將開發者與平台工程師雙雙從重複、機械式的繁瑣工作中徹底解放出來。展望未來，標準化實踐、以產品為中心的管理思維與 AI 驅動自動化之間的深度協同，將持續賦能團隊將精力聚焦於真正重要的事情：推動業務創新、創造商業價值，以及向終端使用者交付高品質的體驗。未來屬於那些致力於建構智慧生態系的人們——在那樣的世界裡，系統具備自我最佳化能力，而平台團隊則能專注於引領下一代數位成功的高階戰略架構。

### 💡 讀者思維：別讓內部平台成為另一座更難用的象牙塔
過去十年我們歷經了「DevOps 拯救世界」的幻滅期——當維運責任直接丟給應用開發者時，換來的往往不是極速敏捷，而是大家都被 YAML、Docker、Helm 和 Terraform 的龐大認知負擔壓垮。平台工程的真諦不是「平台團隊再做一套酷炫但沒人想用的 Web 入口」，而是**以產品經理的同理心，為開發者打造阻力最小的『鋪好之路』（Paved Road）**。如果你的內部開發者平台（IDP）讓工程師覺得比直接敲 `kubectl` 還麻煩，那這座平台在商業上就已經失敗了。

### 🎯 核心精華萃取
1. **認知負擔（Cognitive Load）是唯一的北極星指標**：任何自動化如果沒有實質降低開發者的心智耗損，就只是把複雜度從左口袋換到右口袋。
2. **Platform as a Product（平台即產品）**：平台團隊是內部服務商，開發者是真實顧客。不要用強制命令推規範，要用極致體驗吸引他們主動使用。
3. **技術指標要能翻譯成商業語言**：管理層聽不懂 DORA 指標的微幅波動，但他們聽得懂「新服務上線時間從 3 週縮短為 10 分鐘，等於每年能多驗證 5 個商業假設」。

### ⚠️ 實務踩坑警報
* **切忌「閉門造車」**：在沒搞清楚團隊最痛的卡點前，不要急著自建龐大的 Backstage 實例。最棒的鋪好之路往往是從一份被千錘百鍊過的標準模組開始。
* **小心「偽自助（Fake Self-Service）」**：UI 介面填完表單後背後還是在開 Jira 工單給維運手動審核，這不是自助，這是為官僚流程披上數位糖衣。
