# 對話式介面

對話式介面（Conversational Interfaces）正逐漸成為現代平台工程中不可或缺的關鍵層。隨著平台功能日益強大並融入組織知識，開發者需要更簡便的方式與之互動，特別是在面對**基礎設施即程式碼**（**IaC**）、CI/CD 管線或標準化服務範本時。開發者不再需要依賴翻閱文件或在儲存庫中搜尋，而是可以用自然語言描述他們的需求，讓平台主動引導他們完成操作。

這些介面為團隊提供了一種更直覺的方式來採用平台功能、探索「鋪好之路」（Paved Roads），並在無需死記硬背架構模式或底層細節的情況下生成一致的產物。當對話式工具與組織上下文脈絡相結合時，能幫助開發者更快啟動任務、更自由地探索解決方案，並從一開始就與平台標準保持一致。

在本章中，我們將探討對話式介面如何增強平台工程工作流程，以及它們如何與**模型上下文協議**（**Model Context Protocol, MCP**）等系統整合，以程式化方式存取平台功能。透過實際範例，我們將深入剖析 AI 輔助互動如何在強化一致性並降低認知負擔的同時，精準呈現合適的範本、管線與設定。

在實作初期明確界定系統邊界非常有助益，因為對話式系統在被允許執行的權限範圍上存在著顯著差異。這類系統可能僅用於探索並解釋現有的資源；它可能生成產物以供人工審核；它可能透過既有的審批工作流程提出變更提案；或者它可能直接針對生產環境執行變更。每往前邁出一步，其影響範圍（Blast Radius）就會隨之擴大，對周邊治理機制的要求也隨之提升。我們在本章中所構建的系統，嚴格止步於探索、解釋與提案階段。任何最終套用到叢集的變更都必須透過 Pull Request（PR）進行，並由人工工程師手動審核合併。

在本章中，我們將涵蓋以下主題：

* 平台工程對話式 AI 工具概覽
* 將對話式介面與模型上下文協議（MCP）整合
* 實戰示範：AI 輔助的平台任務
* 當前 AI 工具在平台工程中的局限性
* 內嵌知識結構（Embedded Knowledge Structures）的價值主張

讀完本章後，你將了解對話式 AI 如何成為內部平台的延伸，實現兼顧生產力與標準化的意圖驅動工作流程。

# 實戰技術需求

本章的實戰示範將構建一個可運作的開發者入口網站（Developer Portal），並將其連接到真實運行的 Kubernetes 叢集。所有內容均在單一主機本地運行，因此你不需要為平台本身準備雲端帳號。唯一的外部依賴是聊天助理背後的模型提供商。

要跟隨本章進行操作，你需要：

* Docker、`kind` 與 `kubectl`。安裝指令稿會建立名為 `agentic‑platform` 的本地 `kind` 叢集，並預先安裝好 Metrics Server 與 Argo CD。

* 擁有 Amazon Bedrock 存取權限的 AWS 帳號，或 OpenAI API 金鑰。

以下版本是撰寫與測試本章內容時所採用的基準。Backstage 演進非常迅速，這些實驗刻意鎖定了特定版本，而非盲目追蹤最新發行版：

* `@aws/genai‑plugin‑for‑backstage` 0.5.0 與 `@aws/genai‑plugin‑for‑backstage‑backend` 0.7.1
* `@aws/genai‑plugin‑langgraph‑agent‑for‑backstage` 0.7.2
* `@backstage/plugin‑mcp‑actions‑backend` 0.1.9
* Argo CD v3.0.21

這些版本約束至關重要。`create‑app` 的 0.8.x 及更新版本採用了 Backstage 的新版前端系統，本章中的檔案修改將無法直接適用。Backstage 1.49.0 及更新版本宣告了一個目前尚無 Factory 提供的服務引用，這會導致 Catalog、Scaffolder 與 MCP Actions 外掛無法正常啟動。MCP Actions 後端鎖定版本也是基於同樣的約束：0.1.10 及更新版本帶有該依賴並會以相同方式報錯，因此 0.1.9 是能在 1.48.0 上正常啟動的最後一個版本。

# 平台工程對話式 AI 工具概覽

正如我們在引言中所見，對話式介面為開發者存取與使用平台功能提供了一種更自然的方式。為了理解這一轉變為何具有深遠意義，我們有必要重新回顧現代平台工程中最重要的抽象概念之一：Kubernetes Operator。

Operator 徹底改變了團隊編碼維運知識的方式。Operator 不再僅僅依賴指令稿、應急操作手冊（Runbooks）或人工介入，而是透過領域專屬的維運知識擴展了 Kubernetes 的控制器模式（Controller Pattern），持續比對使用者定義的**期望狀態**（Desired State）與叢集中運行的**實際狀態**（Actual State）。當兩者不一致時，Operator 會自動採取修正措施。

從本質上講，Operator 允許開發者表達意圖：

* 「我需要一個長這樣的資料庫。」
* 「我需要一個具備這些特性的訊息佇列。」
* 「我需要一個依此方式配置的叢集外掛。」

Operator 接收透過自訂資源定義（CRD）宣告的資源，這些資源描述了更高階的抽象概念，並將該意圖轉化為實作所需的低階維運步驟。使用者無需管理備份、副本或容錯移轉邏輯；Operator 會全權處理這些複雜性。*圖 5.1* 展示了這種調諧（Reconciliation）模式。

![](./imgs/B34160_5_1.png)

圖 5.1：Kubernetes Operator 模式：使用者在自訂資源中宣告意圖，Operator 自動調整叢集以達成匹配

這種從「一步步指示系統該怎麼做」轉變為「簡單描述期望狀態」的跨越，標誌著平台工程的重要轉折點。它證明了「意圖」是一種強大的抽象機制：一旦平台理解了你想要什麼，它就能將其餘部分自動化。

對話式 AI 工具將同樣的哲學延伸到開發者在日常工作中與平台的互動方式。開發者不再需要透過 YAML 或 CRD 來表達意圖，而是直接使用自然語言。諸如 Kiro、GitHub Copilot 與 Anthropic Claude 等工具，將這種能力直接帶入了整合開發環境（IDE）、終端機或聊天介面中。

這些工具在平台工作流程中扮演著不同的角色，這種職責定位的差異遠比單純的功能對比更有參考價值。Kiro 是 AWS 目前提供的代理式開發環境，圍繞規格驅動開發（Spec-driven Development）構建：它不再是一問一答式地回應提示詞，而是依據書面規格進行實作，這非常適合預先知曉變更意圖、且對一致性的要求高於速度的平台工作。GitHub Copilot 深度錨定在程式碼庫與 Pull Request 中，因此在程式碼審查與專案骨架生成等平台場景中表現得自然流暢。Anthropic 的 Claude 則可透過 IDE、命令列介面（CLI）與 API 存取，其對 MCP 的原生支援使其成為平台團隊希望將內部系統開放為工具、而非綁定固定整合方案時的常見首選。

這些工具在平台情境下所共享的核心價值並非單純的程式碼生成本身，而是開發者可以從提出一個問題出發，而非面對空白檔案手足無措，並獲得符合組織內部規範的專案雛形與解答。典型場景包括：構建符合平台標準的服務骨架、解釋陌生的 Manifest 設定檔或模組，以及在無需閱讀整套內部文件的情況下找到官方認可的最佳實踐。

在深入探討之前需要提出一項警示。該領域的產品功能與整合生態更迭極為迅速，針對特定工具支援情況的描述往往具有較短的時效性。本章所探討的模式其生命力遠長於實作它們的單一產品：將模型錨定在組織知識中、將平台功能開放為職責單一的工具，並將變更引導至現有的審批工作流程中。凡是我們提及具體工具之處，請務必查閱其官方文件以獲取最新資訊。

這項警示並非空穴來風。如果你過去曾使用過 Amazon Q Developer（在此領域的早期資料中經常被提及），Kiro 便是其技術演進的延續。AWS 已經宣布結束對 Q Developer IDE 外掛及付費訂閱的支援。新用戶註冊已於 2026 年 5 月 15 日關閉，現有 IDE 外掛的支援將於 2027 年 4 月 30 日終止。AWS 管理主控台、Slack 與 Microsoft Teams 中的 Amazon Q Developer 則不受此變更影響。我們提及 Kiro 是因為它是目前的正式產品，但此處描述的架構模式將遠比任何具體產品名稱更加持久。

使這些工具在平台工程中大放異彩的關鍵，在於它們能夠融合兩類不可或缺的上下文脈絡：

* **本地上下文（Local Context）**：開發者工作區中的專案結構、語言、設定檔與相依套件。
* **組織知識（Organizational Knowledge）**：由平台團隊梳理沉澱的規範、IaC 模組、平台範本、架構標準以及黃金路徑（如*[第 4 章](ch04.html)*所探討）。

當這兩種來源結合在一起時，對話式介面便能將開發者的意圖轉化為符合組織標準的專案骨架、設定檔或自動化流程，正如 Operator 在 Kubernetes 內部將宣告式意圖轉化為實際維運動作一樣。

這意味著開發者不再需要從空白檔案開始，也不必到處尋找「合適的參考範例」。他們只需表達自己的訴求，平台便能提供一個立足於組織標準的堅實起點。對平台團隊而言，這使得「鋪好之路」更容易被發現，降低了支援負擔，並有助於在大規模協同中維護架構一致性。

在許多方面，對話式 AI 實質上成為了面向使用者的 Operator 等價物：這是一個接收意圖、應用專業知識並產生成就該意圖所需結構的機制。這種比喻很有啟發性，但也不應過度推演。Operator 會持續且確定性地朝向宣告的狀態進行調諧；而對話式系統則產生一份提案，且該提案在不同執行階段可能會存在差異。兩者的相似之處在於互動的形態，而非執行層面的保證。這正是為什麼對話層應置於受控工作流程的前端、而非取而代之的原因，也是為什麼本章中的每一項變更都必須經過嚴格審查的 Pull Request 才能套用到叢集。

# 將對話式介面與模型上下文協議（MCP）整合

對話式介面所依賴的不僅僅是語言理解能力。它們還需要一種可靠的方式，以可預測且受治理的方式與平台系統互動。模型上下文協議（MCP）為向 MCP 客戶端公開這些能力提供了標準化途徑。當對話式介面負責解讀意圖並將自然語言轉化為結構化請求時，MCP 伺服器則可透過受控的協議邊界開放平台動作與上下文。

先前我們探討了 MCP 如何允許 AI 系統檢索組織知識，例如範本、服務定義、架構模式與設定標準。這種檢索能力有助於確保對話式介面產生的建議能夠準確反映組織所期望的資源構建方式。然而，檢索僅僅是 MCP 的一面。MCP 同樣可以開放工具（Tools），允許 AI 調用受控的平台動作。

MCP 的核心概念是**工具（Tool）**。工具代表平台團隊選擇對外開放的特定能力。每個工具都明確定義了其功能、預期的輸入參數，以及在執行動作前所需的驗證步驟。這些定義為更安全的對話式自動化提供了保障，因為每項操作都必須經過明確註冊且可被驗證與治理的能力管道。

工具是我們在本章中使用最多的基語（Primitive），但它們並不是 MCP 的全部，若將兩者混為一談，容易把該協議窄化為單純的遠端函式呼叫標準。MCP 定義了三種核心基語：**工具（Tools）**是模型可以調用且可能產生副作用的動作；**資源（Resources）**是伺服器提供給模型查閱的唯讀上下文，剛才提到的檢索功能在語義上更自然地映射到資源而非工具；**提示詞（Prompts）**則是伺服器提供的可重用、參數化範本，用於標準化特定請求的表達方式。平台團隊需要決定開放哪些基語，這種區分至關重要，因為它們面臨的安全考量截然不同：資源涉及資訊揭露，而工具則涉及實際行動。

釐清各組件在此架構中所扮演的角色同樣重要，因為這些術語將貫穿全章。在 MCP 架構中，**主機（Host）**是使用者與之互動的應用程式；**客戶端（Client）**是主機內部負責管理協議連線的組件；**伺服器（Server）**則負責暴露工具、資源或提示詞。在本章中，Backstage 進行了一次性動作註冊：入口網站內的聊天助理直接從註冊表中調用選定的動作，而 MCP Actions 後端則將這些相同的動作公開給外部 MCP 客戶端。

驗證（Authentication）與授權（Authorization）應當落在平台側的工具邊界上，而非交由模型處理。這是最值得深刻理解的核心原則。模型只負責產生調用工具的請求；它不應持有平台憑證，也不應直接存取底層平台系統。該調用是否被允許、以及以何種身分執行，完全由後端動作或 MCP 伺服器的邊界來裁決，在此處可以嚴格實施授權與稽核控制。當我們稍後在本章中將聊天助理連接到叢集時，會重新深入探討其實作細節及其局限性。*圖 5.2* 展示了這種代理與伺服器之間的互動關係。

![](./imgs/B34160_5_2.png)

圖 5.2：代理透過 MCP 伺服器存取平台功能，每個伺服器僅公開一組狹窄且明確定義的工具集

當對話式系統生成 Terraform 檔案、Kubernetes 清單或其他產物時，理論上它可以直接將這些變更套用到環境中。然而，在本書中，我們專注於能夠保護既有部署策略與治理模型的方法。一種可行的做法是公開一個 MCP 工具，由其建立分支、提交生成的資源並發起 Pull Request。這正是代理在*[第 7 章](ch07.html)*中所獲得的工具。我們在本章後續構建的助理則更為審慎，保持純唯讀狀態，以便能獨立審視寫入路徑。

組織的持續整合（CI）工作流程隨後會執行常規驗證，包括單元測試、原則檢查與安全掃描。當 Pull Request 獲得批准並合併後，部署步驟將透過組織現有的交付機制執行。這可能涉及 GitOps 控制器自動偵測變更並套用，或是傳統的持續部署管線。關鍵在於：**透過對話式介面建立的變更，遵循著與其他人工作業完全相同且可稽核的受控路徑。**

平台團隊還可以提供託管式的對話介面。託管介面免去了開發者安裝外掛或設定本地環境的麻煩。託管介面能集中管理身分驗證、授權、組織知識與治理原則。對話的可稽核性仍然取決於平台團隊所設定的記錄日誌、留存原則、身分識別與存取控制。

為了理解 MCP 與對話式互動如何協同運作，請看一個典型範例：某位開發者需要部署一個三層式應用架構（Three-tier Application）。這個流程展示僅作為概念說明，旨在展現各組件如何銜接；並非後續章節要實作的動手實驗，我們後續也不會再回顧它。開發者開啟託管對話介面並描述需求：一個 API 層、一個後端服務，以及一個具備特定擴展與安全約束的資料庫。*圖 5.3* 顯示開發者以自然語言描述應用程式需求。

![](./imgs/B34160_5_3.png)

圖 5.3：開發者使用自然語言描述三層式應用，而非手動撰寫設定清單

對話介面解讀該請求，並利用檢索增強生成（RAG）與 MCP 調取組織的範本、參考架構與標準規範。結合這些上下文，它生成所需的資源清單，並自動套用所有命名慣例、標籤與安全要求。在平台組裝好最終的資源集合後，MCP 工具將產生的檔案提交至對應的程式碼庫並開啟 Pull Request。*圖 5.4* 總結了這一概念性流程。

# 實戰示範：AI 輔助的平台任務

在這個實戰示範中，我們將走過一個真實的平台工程環境搭建過程，並逐步引入對話能力。我們並非一上來就導入 AI，而是從熟悉且已就緒的正式維運基準架構起步，隨後在其上疊加智慧層。這使我們更容易看清對話式介面究竟帶來了哪些增量價值，以及為什麼將其整合進現有平台工作流程時最能發揮威力。

有必要預先設定本次示範的涵蓋範疇。本示範所展示的平台任務主要為「基礎設施即程式碼生成」與「服務骨架搭建」：Backstage 範本產出一套完整的 Kubernetes 清單（Deployment、Service、ConfigMap 與水平 Pod 自動擴展器 HPA）以及交付它們的 Argo CD Application，且一切均透過 Pull Request 進行，而非直接寫入叢集。我們在其上構建的對話層使這條「鋪好之路」變得容易被發現，並在部署後解釋叢集運行現狀。編寫 CI/CD 管線定義與 AI 輔助的語法檢查（Linting）是這項技術的相鄰應用場景，它們遵循相同的「知識錨定 + 受控寫入」模式，但我們在此處暫不展開建置。

## 透過 Backstage 與 GitOps 建立平台基準線

我們首先以 Backstage 作為開發者入口網站、以 GitOps 作為部署模型來建立平台工程基準線。該基準反映了當今許多平台團隊構建內部平台的方式，並作為後續章節引入對話能力時的穩定參考點。*圖 5.5* 顯示了示範中使用的 Backstage 範本目錄。

所有平台變更均透過 Git 進行管理。當開發者依據 Backstage 範本建立新應用時，生成的設定會被提交至 Git 儲存庫，並透過 Pull Request 進行審查。這確保了治理、稽核與協作機制能與既有的工程實踐保持高度一致。*圖 5.6* 顯示了隨後產生的 Pull Request。

![](./imgs/B34160_5_6.png)

圖 5.6：由 Backstage 範本自動發起的 Pull Request，攜帶生成的 Kubernetes 清單

部署作業由 Argo CD 負責，這是一個 GitOps 控制器，負責持續調諧 Git 中定義的期望狀態與 Kubernetes 叢集中運行的實際狀態。變更無需手動觸發部署，只需合併 Pull Request 即可生效。我們在此選用 Argo CD，是因為其 `ApplicationSet` 控制器能自動偵測組件儲存庫中的新應用，因此從範本生成的服務無需人工手動註冊即可自動部署。如果你的組織採用 Flux，同樣可以達成此目標，但替換過程並非一對一等價。Flux 將任務拆分給宣告來源的 `GitRepository` 與調諧路徑的一或多個 `Kustomization` 資源，且它沒有直接對應 `ApplicationSet` Git 產生器的機制。因此，本章所依賴的逐應用探索邏輯必須重新構建：要麼做成列出所有應用目錄的頂層 `Kustomization`，要麼為每個應用提交獨立的 Flux `Kustomization` 並由父級調諧。此外，每個應用還需要自己的 `Namespace` 清單，因為 Flux 不像此處的 `CreateNamespace` 同步選項那樣會自動建立命名空間，且儲存庫憑證也採用不同的 Secret 格式。因此本實驗僅針對 Argo CD 設計。這種模型強化了明確的職責分離：Backstage 擷取意圖、Git 表達期望狀態，而叢集自動收斂。*圖 5.7* 顯示在 Pull Request 合併後，應用程式在 Argo CD 中已同步且處於健康狀態。

![](./imgs/B34160_5_7.png)

圖 5.7：Pull Request 合併後，Argo CD 顯示 my-first-app 已同步且狀態健康

應用範本定義了服務在平台中如何組織結構、部署與註冊。我們使用基於 Kubernetes 的 Web 應用範本進行端到端示範，涵蓋 Backstage 中的服務註冊與透過 GitOps 實現的自動化部署。一旦部署完成，服務在叢集與開發者入口網站中均清晰可見，從而閉環了「建立」與「維運」之間的反饋迴路。

該基準線刻意未包含任何 AI 或對話功能。其目的在於建立一個許多組織已經非常熟悉的清晰平台工作流程。從這個堅實基礎出發，更容易看清對話式介面到底帶來了什麼，以及為什麼將其疊加在既有平台抽象之上比起孤立引入要有效得多。

## 為 Backstage 引入對話式介面

在具備了平台基準線之後，我們將對話式介面引入 Backstage。此步驟的目的並非打造一個無所不能的平台助理，而是在開發者入口網站內部建立最精簡的 AI 互動介面。

利用 AWS GenAI for Backstage 外掛，我們加入了一個 AI 驅動的聊天介面，開發者可直接從入口網站的導覽列存取。該聊天助理背後由**大型語言模型**（**LLM**）支援，例如 Amazon Bedrock 託管的模型或 OpenAI 等替代提供商。在此階段，該助理僅作為通用對話介面運作。

具體而言，這涉及三個後端套件與一個前端套件。後端採用 `@aws/genai‑plugin‑for‑backstage‑backend` 提供聊天 API、`@aws/genai‑plugin‑langgraph‑agent‑for‑backstage` 提供代理實作，以及 `@backstage/plugin‑mcp‑actions‑backend` 提供兩者所依賴的動作註冊表（Actions Registry）。註冊順序至關重要：動作註冊表必須在 GenAI 外掛之前加入，否則外掛在啟動時將無法解析它。前端則使用 `@aws/genai‑plugin‑for‑backstage` 提供聊天頁面組件與側邊欄入口。儲存庫中的 *Lab 2* 列出了精確的指令與檔案編輯步驟。

模型提供商在 `app‑config.yaml` 中代理的 `langgraph` 區塊下配置，切換提供商僅需替換一個巢狀鍵值。此處採用的配置選擇了 Amazon Bedrock：

```yaml
genai:
  agents:
    general:
      langgraph:
        messagesMaxTokens: 150000
        bedrock:
          modelId: 'global.anthropic.claude-sonnet-4-5-20250929-v1:0'
          region: us-west-2
```

完整配置（包括 OpenAI 變體、精確的安裝指令以及對 App.tsx 和 Root.tsx 的修改代碼）請參見儲存庫中的 Lab 2：

[`https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering/tree/main/chapter-05/2-add-chat-assistant`](https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering/tree/main/chapter-05/2-add-chat-assistant)

將 `bedrock` 區塊替換為包含 `apiKey` 的 `openai` 區塊，即可將助理切換至 OpenAI，無需對本章其餘部分進行任何更動。實戰中的其他部分完全獨立於底層模型提供商：目錄動作、Kubernetes 動作與治理模型均構建於其上層。使用 Azure 或 Google Cloud，或是運行自託管模型的讀者，預期也將在此同一個配置鍵進行替換，但在確定選型前建議查閱外掛文件以確認其支援的提供商。

由於該外掛即將進入由整個工程團隊共享的入口網站，其成熟度值得特別說明。GenAI 外掛由 AWS Labs 作為 `backstage‑plugins‑for‑aws` 專案的一部分進行維護。它們處於積極開發階段且版本仍低於 1.0，這也是本章鎖定精確版本而非追蹤最新發布的原因。請如同對待共享系統中的任何 pre-1.0 依賴項一樣對待它：鎖定版本、關注變更日誌，並在向開發者開放前完成升級測試。*圖 5.8* 顯示了在加入平台專屬動作之前的助理狀態。

![](./imgs/B34160_5_8.png)

圖 5.8：在進行任何平台整合之前的聊天助理，無法回答當前存在哪些服務

從平台架構角度來看，這是一個刻意受限的設定。助理可以回答有關軟體開發、雲端概念或平台工程實踐的通用問題，並以排版工整的 Markdown 格式進行回應。然而，它對組織內部的平台、服務、儲存庫或運行環境完全一無所知。

這種限制是刻意為之且極具啟發性的。助理並未連接到 Backstage 的目錄、技術文件或任何維運系統。其回應完全基於模型的預訓練資料以及配置時給定的靜態提示詞。因此，儘管它可以用於學習或技術探索，卻無法可靠地支援平台特有的工作流程。

以這種孤立的形式引入對話介面，及早揭示了一個關鍵結論：**光靠對話式 AI 本身對於平台工程是遠遠不夠的**。在缺乏組織上下文的情況下，助理無法回答「存在哪些服務」、「誰是負責人」或「叢集中目前正在運行什麼」等問題。這種鴻溝凸顯了通用聊天機器人與具備「平台感知能力」的專業助理之間的本質差異。

與此同時，將聊天介面直接內嵌至 Backstage 是一項關鍵的架構決策。透過將對話入口置於開發者入口網站內部，我們確保了未來的能力是構建在既有的平台抽象之上，而非演變為另一套孤立工具。開發者無需切換上下文或適應新介面；助理自然而然地成為了平台自身的有機延伸。

此步驟建立了對話基礎。在下一節中，我們將透過把助理連接到 Backstage 的服務目錄，開始彌合上下文鴻溝，使其能夠對真實的平台實體進行推理，而非僅停留在抽象概念層面。

## 透過 Backstage 目錄知識豐富聊天助理

在獨立引入對話式介面之後，下一步是賦予助理對平台本身的感知能力。我們透過將聊天助理連接至 Backstage 的軟體目錄與技術文件系統來達成這一目標。

在此階段，我們為助理擴展了一組輕量的 Backstage 內建動作（Actions），使其能夠查詢目錄實體並檢索技術文件。這些動作提供了唯讀權限，用以存取開發者已在 Backstage UI 中使用的相同事實來源，例如已註冊組件、所有權元數據與 TechDocs 內容。

完成這項整合後，助理便能開始對真實的平台實體進行推理，而非僅限於抽象概念。開發者可以詢問存在哪些組件、某個服務由誰負責，或是查詢特定應用程式的詳細資訊。助理還可以檢索技術文件，利用 TechDocs 中已沉澱的資訊回答問題，將相關資訊精準呈現給開發者，無需他們手動翻閱多頁文件。*圖 5.9* 顯示助理基於目錄上下文進行回答。

![](./imgs/B34160_5_9.png)

圖 5.9：在註冊 Backstage 動作後，助理依據真實的目錄實體回答問題

這標誌著能力的重大飛躍。助理不再是泛泛而談的聊天機器人，而是進化為具備平台感知能力的助理。其回應立足於組織知識，反映了平台的組織架構與文件規範。更重要的是，這些知識經過了嚴格的梳理與治理：目錄與 TechDocs 本身就是作為日常平台運作的一部分受到持續維護的，因此助理可以直接重用相同的管控機制與組織規範。

然而，此時對平台的認知依然不夠完整。Backstage 目錄所描述的是**應該存在**的狀態：宣告的服務、預期的所有權以及記載的行為；它並不代表平台的即時運行狀態。此時的助理仍然無法回答某個服務當前是否已部署、是否處於健康狀態，或是否正在特定環境中運行。

這種區分是深思熟慮的結果。透過先為助理注入目錄知識，我們在「**宣告的平台架構**」與「**執行期的真實狀態**」之間劃定了清晰的界限。這有助於更清楚地理解隨著助理持續進化，各項整合所扮演的獨立角色。

在此節點上，對話介面已能良好支援服務探索與架構理解，但尚不具備維運洞察力。在下一節中，我們將透過註冊第二組動作，將助理的視角擴展至靜態元數據之外，提供對即時叢集的唯讀觀察視角。

## 透過 MCP 與叢集感知擴展聊天助理

截至目前，對話介面一直建立在靜態的宣告性知識之上。透過將助理連接至 Backstage 目錄與技術文件，它得以對平台中「應該存在」的內容進行推理。下一步則是將此視野擴展至「**實際運行**」的現狀。

為了實現這一點，我們在 Backstage 的動作註冊表（即容納目錄與 TechDocs 動作的同一註冊表）中註冊了四個自訂動作。進行一次註冊即可獲得兩種存取途徑：第一條途徑是我們的入口網站助理——我們在 `app‑config.yaml` 中代理的 `actions` 鍵下依名稱列出這些動作，GenAI 外掛會解析它們並作為工具直接傳遞給模型，程序內運行，中間無需跨網路協議。第二條途徑是 MCP Actions 後端透過 HTTP 運行的 MCP 伺服器，它將這些完全相同的動作發布給入口網站之外的任何原生 MCP 客戶端。這第二扇門特別值得深思，因為它決定了誰可以使用你所構建的能力。平台能力不再只是開發者必須開啟入口網站才能觸及的功能；它們可以直接在正在編寫程式碼的編輯器或終端機中被隨時調用。*Lab 4* 的結尾正是示範了這一點：從完全獨立於 Backstage 的外部客戶端調用 `kubectl_get_pods`。該套件出現在此，既是因為它提供了 GenAI 外掛所依賴的註冊表工廠（正如我們在安裝時所見），也是因為我們的 Kubernetes 模組掛載於其上：該模組在 `mcp‑actions` 外掛 ID 下註冊，這正是該名稱出現在 `pluginSources` 中的原因。無論模型從哪扇門進入，其契約都是完全相同的：每個動作僅暴露一個範圍狹窄、唯讀的能力（例如列出工作負載或描述特定資源），絕不開放任意命令列執行權限。

透過這種整合，助理可以向 Kubernetes 查詢具權威性的執行期即時數據。它可以列出特定命名空間下的 Pod、Deployment 與 Service，或是檢查特定工作負載的詳細狀態。這將助理從單純的文件與探索工具，升級為反映平台即時狀態且具備維運感知能力的智慧介面。

在助理側，整套整合正是這段綁定設定：

```yaml
backend:
  actions:
    pluginSources: [catalog, aws-genai, mcp-actions]
genai:
  agents:
    general:
      actions:
        - get-catalog-entity
        - search-catalog
        - search-techdocs
        - kubectl_get_pods
        - kubectl_get_deployments
        - kubectl_get_services
        - kubectl_describe_pod
```

已註冊但未在此處列出的動作對模型而言是隱形不可見的。如果助理表示它無法執行你預期它能做的事情，此列表是首要排查之處。

每個動作都是一份小巧、明確的契約。定義中宣告了工具名稱、功能描述、接受的輸入參數以及傳回資料的結構型態；模型只能嚴格按照這些約定來調用它。例如，Pod 清單查詢動作宣告了一個輸入參數（namespace），以及一個輸出欄位（包含以字串表示的 `kubectl` 執行結果的物件）：

```typescript
actionsRegistry.register({
  name: 'kubectl_get_pods',
  title: 'Get Kubernetes Pods',
  description: 'Get pods in a Kubernetes namespace',
  schema: {
    input: (zod) => zod.object({
      namespace: zod.string().default('default'),
    }),
    output: (zod) => zod.object({
      result: zod.string(),
    }),
  },
  action: async ({ input }) => {
    const result = await execKubectl([
      'get', 'pods', '-n', input.namespace, '-o', 'json',
    ]);
    return { output: { result } };
  },
});
```

這是簡化後的程式碼視圖；儲存庫中的版本還為每個欄位附加了詳細說明，這正是模型在決定如何調用該動作時所依據的資訊。註冊表會根據輸出綱要（Schema）校驗傳回值，這也是為什麼該動作將字串包裝在物件中而非直接裸露返回的原因。註冊所有四個動作並處理 `kubectl` 調用的完整模組是儲存庫中的單一 TypeScript 檔案，*Lab 4* 提供了加入該模組的逐步指南：

[`https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering/tree/main/chapter-05/4-add-kubernetes-actions`](https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering/tree/main/chapter-05/4-add-kubernetes-actions)

在將該端點暴露到真實生產環境之前，有一項重要注意事項必須知曉：MCP 介面發布的是註冊表中所容納的所有內容，而非僅限於代理所綁定的縮減清單，因此它暴露的能力可能超出你的聊天助理所能觸及的範圍。在本章的設定中，代理擁有 7 個唯讀動作，但該端點卻對外發布了 13 個動作，其中包括兩個對目錄進行寫入的動作。在將權杖交付他人之前，請務必先審查工具清單，並像對待其他憑證一樣為其配置嚴格的權限範圍。

在上述定義中完全不存在自由格式的指令參數，這正是架構設計的核心意圖所在。助理無法構建任意的 `kubectl` 調用，因為它唯一能控制的只有 `namespace` 字串。擴展助理的功能必須經過平台團隊註冊並審核新動作的嚴謹流程，這是一項主動的架構決策，而非隨意因使用者提示詞語氣而產生的副作用。

在將此方案運用到示範以外的環境前，有兩項至關重要的考量。第一項是**身分識別（Identity）**。在此實作中，動作由 Backstage 後端執行 `kubectl`，這意味著每個請求都是以「後端自身的身分」抵達叢集，而非以發問的開發者身分抵達。在本地叢集中這無關痛癢；但在共享環境中影響深遠：任何能打開聊天視窗的開發者，都能看見後端有權檢視的一切內容，這意味著開發者個人的 Kubernetes 權限未被強制套用，所有請求均以後端身分獲得授權。正式生產環境中應將後端綁定到限縮於最小實用資源集的專用 ServiceAccount，並將發出請求的使用者身分透傳至叢集調用中，以確保既有的權限管控持續生效。

第二項考量是**唯讀並不等同於絕對安全**。具備讀取 Pod 權限的角色通常也能讀取 Pod 規範（Pod Spec），而這些設定往往包含環境變數、掛載的 Secret 名稱以及資料庫連線字串。助理讀取到的任何內容都可能出現在聊天記錄中，而對話記錄通常會被持久化留存。在規劃 ServiceAccount 權限範圍時，應徹底排除 Secret，並將描述 Pod 的權限視為一項敏感的資料揭露決策，而非純粹追求便利。*圖 5.10* 展示了透過唯讀動作傳回的即時 Pod 狀態結果。

![](./imgs/B34160_5_10.png)

圖 5.10：助理透過 kubectl_get_pods 動作回報擷取到的即時 Pod 狀態

這種區分是決定性的。執行期感知彌合了意圖與現實之間的斷層。助理不再依賴基於範本或目錄條目的臆測；相反，它透過經核准的動作直接從叢集擷取最新資訊。因此，開發者可以詢問「某個應用是否已部署」、「工作負載是否健康」或「某服務運行於何處」，並獲得基於平台即時現狀的準確答案。

同樣重要的是這套存取機制的實作方式。語言模型與平台之間的界線正是動作註冊表——無論模型是在程序內直接存取（如本示範），還是透過 MCP 端點存取（如外部客戶端）；當這道界線需要跨越網路時，MCP 正是其標準化形態。動作均經過明確註冊、校驗與治理，因此助理只能執行它被明確授權的操作。在此處，這些操作被刻意設定為唯讀，在保持助理純粹觀察屬性的同時，依然能交付極具價值的維運洞察。*圖 5.11* 展示了當開發者請求超出邊界時，助理在使用者側的具體表現。

![](./imgs/B34160_5_11.png)

圖 5.11：助理因未註冊任何寫入動作而明確拒絕修改 Deployment

*圖 5.11* 是本章中最重要的一張截圖，值得細細品味，因為乍看之下它彷彿是一次執行失敗。開發者要求助理修改某個 Deployment 的 CPU 配額限制，助理斷然拒絕。它之所以拒絕，是因為根本不存在能讓它照做的工具：唯一註冊的 Kubernetes 動作全是唯讀操作。**這正是安全防護護欄（Guardrail）完全按照預期設計在發揮作用**。這並不是模型主觀決定要保持謹慎，也不是因為提示詞中寫了一條可能被巧妙措辭繞過的約束指令。根本原因在於：**這項能力壓根就不存在**。

不過，該回應中的一個細節確實需要糾正。助理建議使用 `kubectl patch` 與 `kubectl edit` 來進行變更。這些指令固然能生效，但對本平台而言卻是錯誤的修復路徑：對叢集進行指令式（Imperative）的臨時修改，在 Argo CD 下一次對齊 Git 狀態時會被無聲無息地覆蓋還原，且不會在儲存庫中留下任何可供同儕審查的紀錄。正確的做法是針對 Manifest 清單發起 Pull Request，這正是下一節所探討的內容。這是一個很好的提醒：立足於通用知識的模型傾向於給出泛用解答，除非平台主動為其提供更具體的指引。

在此階段，對話式介面已成為名副其實的維運助理。它將來自 Backstage 目錄的組織知識與來自 Kubernetes 的即時平台狀態緊密結合，並透過開發者入口網站內的單一自然語言介面完整呈現。

然而，助理本質上仍然是觀察者。它能洞悉並解釋平台狀態，但它不會修改狀態，在本章結束前也不會賦予它這項權限。下一節將追蹤一個請求從聊天視窗出發直到 Pull Request 合併的完整路徑，展示究竟由哪個組件執行寫入，以及為何採取這種架構設計。

## 從洞察邁向行動

一旦助理具備觀察平台的能力，下一個自然浮現的問題就是：變更究竟是如何發生的？這正是對話式介面最常被誤解的地方，因此值得給出精準的答案：**在本章中，助理絕不執行實質寫入，而這種架構設計正是最穩固的選擇。**

想像一位開發者詢問如何搭建新服務，或是為何某個部署處於非健康狀態。助理依據其可讀取的資訊作答：透過目錄動作，它找到合適的範本，解釋該範本會產生什麼產物，並說明它需要哪些參數；透過 Kubernetes 動作，它描述發生故障的 Pod 並指出需要修改的 Manifest 清單。但它本身不持有任何修改叢集或儲存庫的工具。開發者拿到這個解答後，前往 Backstage Scaffolder 並執行該範本——**執行寫入動作的是 Scaffolder，而不是助理。**

從那一刻起，既有的 CI/CD 與 GitOps 流程全面接管。驗證檢查運行、審批生效，部署透過組織早已信賴的既organic機制展開。對話介面成為了通往平台的引導式入口，而非繞過既有防護的後門捷徑。

本章使用的範本在發布階段結束時，會自動建立分支、提交生成的清單，並向組件儲存庫發起 Pull Request。這些清單正是前文*圖 5.6*中展示的 ConfigMap、Deployment、Service 以及水平 Pod 自動擴展器（HPA）。一旦 Pull Request 審核通過並合併，Argo CD 的 `ApplicationSet` 便會自動偵測到新目錄並展開部署，這正是*圖 5.7*所呈現的健康狀態。開發者在對話中表達意圖；平台產出可供審查的變更；控制器調諧叢集以達成期望狀態。

這完美閉環了本章開篇所提及的哲學。Kubernetes Operator 以自訂資源形式接收意圖，注入維運知識，並朝向該資源所描述的狀態調諧叢集。我們構建的對話層承擔了該模式面向使用者的前半段，且這種映射維持著合理的邊界：提示詞承載意圖，Pull Request 提出期望狀態變更，而 GitOps 控制器只有在該變更通過審核並合併後才執行調諧。對話式介面革新了意圖的表達形式；但它完全沒有改變變更進入生產環境的嚴肅路徑。

將寫入路徑嚴格保留在範本中而非交由助理執行，是一項經過深思熟慮的架構抉擇，這也是為什麼*圖 5.11*中的拒絕是正確的行為，而非需要彌補的缺陷。範本經過嚴格審查、具備版本控制且高度參數化；其輸出是完全可預測的。直接擁有叢集寫入權限的助理則無法提供同等水準的可審查性與可預測性。*[第 7 章](ch07.html)*將重新檢視這一邊界，並賦予代理真正的變更工具，但那是透過開放一個範圍狹窄、僅能發起 Pull Request 的受控動作來實現的，絕非直接寫入叢集。

[`https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering/tree/main/chapter-05/1-backstage-setup`](https://github.com/PacktPublishing/Agentic-AI-for-Platform-Engineering/tree/main/chapter-05/1-backstage-setup)

這種漸進式的演進歷程清楚展示了：當以循序漸進的方式引入對話式介面時，它如何天然融入平台工程之中。從標準的 Backstage 與 GitOps 架構起步，我們加入對話能力、以組織知識充實它、以即時平台感知擴展它，最後賦予其提出受控變更建議的能力。其成果絕非取代既有的平台工作流程，而是在其上疊加一層直覺的溝通層，使平台更易被理解、維運更加安全，且對開發者更具親和力。

# 當前 AI 工具在平台工程中的局限性

儘管前述各節展示了諸多優勢，但當前 AI 工具在應用於平台工程時仍面臨不可忽視的實質局限性。這些系統在生成程式碼與配置設定方面表現優異，但它們先天並不理解特定平台的設計哲學、治理原則或特定時刻的即時維運狀況。若缺乏嚴謹的整合設計，AI 驅動的互動產生的結果往往「表面上看起來正確」，卻與組織規範或當前平台狀況脫節。

在實務中，有六大局限性尤為突出：平台專屬知識的缺失、即時狀態感知的匱乏、模型幻覺及其依賴審批流程進行緩解、多代理編排的複雜性、模型輸出的非確定性，以及系統大規模運行時的成本與延遲挑戰。

## 組織與平台專屬知識

通用型 AI 模型並未內建對特定企業內部標準、黃金路徑或架構決策的認知。它們深諳如何定義一個標準的 Kubernetes Deployment 或 Terraform 資源，但它們完全不知道你的團隊強制要求哪些 Annotation 註解、服務命名的約定規範、哪些模組是經核准的，或者平台內部如何劃分所有權與維運責任。

一旦缺失這些組織專屬知識，AI 生成的產物往往表面上合規，但在細節上卻微妙地偏離了平台標準。關鍵的元數據可能被遺漏、過時的架構模式可能被重複使用，或者生成的定義可能與現有的自動化工具產生衝突。日積月累之下，這些不一致性會割裂平台架構，而非鞏固其既定設計。

這種局限性與模型幻覺緊密交織。當缺乏權威事實來源時，AI 系統往往會自信滿滿地生成在該組織內部根本不存在的配置或引用。將對話介面建立在精心梳理的組織知識之上，並透過受控的動作將其連接至權威系統，是 AI 輔助平台工作流程不可或缺的安全防護。RAG 與 MCP 正是支撐這些目標的兩大關鍵技術機制。

## 即時平台狀態感知的挑戰

除了缺乏組織上下文外，AI 工具本質上也缺乏對平台即時運行狀態的洞察力。模型不可能知曉當前正在運行哪些工作負載、哪些環境處於健康狀態，或者某項資源是否已經存在——除非主動將其連接到管理這些資訊的系統。

當利用 AI 來提出變更建議時，這項缺陷尤為致命。對話介面可能會提出與當前環境衝突的更新、假設引用了早已被刪除的資源，或者忽視了部分叢集故障或進行中的滾動更新等特殊狀況。即便是結構極其優雅的配置，一旦建立在陳舊或殘缺的假設之上，也會引發嚴重的維運事故。

透過受控的動作將對話介面連接至權威系統有助於彌合這一鴻溝。MCP 可以為外部客戶端標準化這類存取途徑，但即時狀態感知必須是深思熟慮、受控且具備高度可觀測性的。缺乏這項能力，AI 輔助的變更將始終面臨脫離平台實際運行現狀的巨大風險。

## 幻覺、治理與審批流程的角色

幻覺（Hallucination）始終是當前 AI 系統的根本局限。在平台工程中，一個錯誤假設所帶來的代價往往極其沉重，可能直接衝擊系統穩定性、安全性或合規性。因此，保留現有的審核與驗證流程絕非權宜之計，而是一項核心架構決策。

將 AI 生成的變更強制引導至 Pull Request、人工同儕審查、自動化測試以及部署關卡，有助於在幻覺滲透至生產環境之前將其及時攔截。這些工作流程提供了人工與自動化雙重監管，使 AI 成為推動安全變更的加速器，而非失控的冒險者。

因此，對話介面應該補充治理體系，而非取而代之。當它們能協助團隊更快產出更優質的變更提案，同時將最終驗證權保留給平台既已信賴的檢驗機制時，才能發揮出最大的價值。

## 多代理編排的複雜度

隨著對話系統的不斷演進，它們往往會裂變為多個專精於不同階段的專屬代理：檢索知識、解讀意圖、驗證配置、查詢平台狀態或提出變更。久而久之，編排這些代理所面臨的架構挑戰，開始與過去從單體架構轉向微服務架構時所經歷的陣痛如出一轍。

專精化固然帶來了靈活性，卻也引入了協同複雜性。如果系統邊界沒有清晰界定，故障追蹤將變得更加困難、職責容易模糊，系統整體行為也可能演變為難以理解的黑盒。諸如 Strands（AWS 推出的開源 SDK，專用於構建圍繞定義工具集進行迴圈推理的代理）等框架有助於應對這項挑戰，它將推理、動作與工具互動在時間維度上的銜接結構化，使多步驟工作流程更具可預測性與可觀測性。我們將在*[第 7 章](ch07.html)*中深入剖析 Strands，屆時將由它來運行正式的維運代理。MCP 透過為各組件之間提供結構化介面與受控動作來輔助這套方案，但這兩者都無法完全免除對嚴謹系統設計的需求。平台團隊仍必須定義清晰的邊界、所有權歸屬與生命週期規則，以防止代理工作流程變得脆弱或難以維護。

平台團隊必須將代理視為頭等架構公民，賦予其明確的所有權、可觀測性與能力邊界。否則，編排所引入的複雜性將直接吞噬 AI 所承諾交付的生產力紅利。

## 非確定性與測試難題

前述的所有局限性主要關乎助理「知道什麼」。而這一條則關乎它「是否能兩次表現完全一致」。面對相同的提示詞、對應完全相同的目錄與叢集狀態，模型可能產生不同的措辭、調用不同順序的工具，甚至推導出不同的結論。對於一般的聊天工具而言，這通常無傷大雅；但對於工程師被要求嚴肅依賴的平台基礎能力來說，這卻是一個實實在在的維運難題。

困難在於傳統的防護手段無法直接套用。平台團隊可以對 Terraform 模組或 Scaffolder 範本進行精準的回歸測試，因為其輸出是確定性且易於比對的。然而，對於「助理是否正確回答了這個問題」，並不存在等價的簡單斷言機制。認真對待此問題的團隊通常會建立一套評估集（Evaluation Set，常簡稱為 Eval）：一組具有標準正確答案的固定測試問題集，在將任何變更推送給開發者之前對其進行評分驗證，其把關嚴格程度如同對待任何常規平台變更一樣。

這在模型升級時尤為重要。模型版本的棄用與更替是依據模型提供商的排程進行的，不受你的意志控制，而更新的模型在處理你的特定任務時並不必然表現更優。缺乏評估集，平台團隊將根本無法察覺某次模型微調是否已經悄然削弱了開發者高度依賴的解答品質。鎖定特定模型版本（如本章配置所做的那樣）只是最基本的底線；真正掌握變更該版本會帶來什麼實質影響，才是核心要求。

## 大規模應用時的成本與延遲

本章中的實戰示範成本極低，因為其規模小巧。然而，正式生產環境中的大規模部署會從兩個極易被低估的面向徹底改變這道算式。在大規模目錄上進行檢索會將大量上下文灌入單次請求中，而多步驟工具調用更可能在助理最終作答前觸發連續多次模型調用。依據模型提供商與架構設計的不同，這兩者都會顯著增加 Token 消耗量，從而推高推論成本。

在推廣普及過程中，延遲（Latency）往往是更直接的致命威脅。相較於一個耗時 15 秒才回答出一個開發者自己打開目錄只需 3 秒就能查到的問題的助理，開發者往往更容易寬恕偶爾犯錯的助理。多步驟工具鏈是導致延遲的常見元兇，因為每一次往返調用都意味著增加一次完整的模型推論週期。將動作集保持在小巧且專精的範圍內（正如我們在此處所做的那樣），既是一項安全架構抉擇，也是一項至關重要的效能最佳化決策。

# 內嵌知識結構（Embedded Knowledge Structures）的價值主張

上一節所探討的各項局限性背後存在著一個共同的根因：**模型先天根本不了解你的平台**。本章所新增的每一項能力，實質上都是在為它賦予存取組織內部早已存在的既有知識的途徑。這項觀察值得被嚴肅看待，因為它從根本上改變了平台團隊思考如何迎接 AI 時代的視角。

助理之所以能在連接到平台團隊早已構建好的架構時瞬間發揮出巨大價值，其背後有著奇妙的巧合：當初構建這些架構完全是基於其他維運目的。沒有人會純粹為了「讓語言模型變聰明」而煞費苦心地維護 Backstage 目錄；人們維護它是為了讓內部開發者能快速找到服務並明確負責人。沒有人會為了改善 AI 輸出而導入 GitOps；人們採用它是為了稽核能力與可靠的回滾機制。然而，事實證明，這兩者恰恰就是智慧助理迫切所需的基石。

## 為什麼 GitOps 與 Backstage 是如此卓越的知識基石

當這兩套系統透過常規平台工作流程進行維護時，它們能提供高度結構化、最新且具權威性的事實來源。

* **Backstage 目錄是組織的強型別模型**：組件、系統、API、負責人與生命週期階段均為明確的結構化欄位，而非需要被揣摩理解的散文。查詢它的助理完全不必猜測某個服務到底歸誰負責。
* **TechDocs 讓技術文件與其描述的程式碼同生共存**：這確保了文件能夠與程式碼保持同步演進。對於知識錨定而言，發生漂移脫節的過期文件比完全沒有文件更加危險，因為它會導致模型產出看似言之鑿鑿卻完全錯誤的回答。
* **Git 承載著透過 GitOps 管理之環境的期望狀態**：伴隨著完整的提交歷史與變更歸屬。針對「此時此刻究竟應該運行什麼」這個問題，Git 給出了精確無誤的權威答案，完全無需依賴任何人的口頭記憶。
* **GitOps 控制器持續將該期望狀態與實體叢集進行調諧**：這使得意圖與現實之間的偏差本身成為清晰可見的指標。

這些基石共同為助理賦予了一般通用模型永遠不可能擁有的能力：一份關於該特定組織如何構建與運行軟體的最新、機器可讀的事實記載。至關重要的是，它們**天然附帶著既有的治理機制**。目錄有明確的所有者、基於 Git 的工作流程有嚴格的審查者，而控制器擁有確定性的調諧迴圈。構建於其上的助理可以直接重用大量現成的治理架構，而無需從零開始設計一套繁瑣的「AI 專屬治理模型」。

## 理想的內嵌式系統藍圖

從本次示範向外推演，一套成熟的內嵌式系統的架構輪廓已清晰可見。它絕非硬生生拼接到平台上的獨立 AI 玩具；它是一項能夠直接讀取平台既有事實來源、並透過平台既有變更流程回寫變更的內建核心能力。

這樣一套系統會將每一個答案堅實錨定在目錄、技術文件以及即時叢集狀態之中，並主動標註引用來源，指明答案究竟是源自哪個目錄實體或哪份 Manifest 清單，以便開發者能進行人工複核。它會將功能暴露為狹窄、經過明確註冊的動作，而非無限制的開放式存取；它會將發起請求的開發者身分貫穿透傳至每次調用中，以確保既有的權限原則持續生效。它所提出的任何變更都將以 Pull Request 的形式呈現，接受與人工編寫程式碼完全相同的檢查與同儕審查。並且，它必須具備極致的可觀測性：清楚記錄執行了哪些動作、代表誰執行，以及執行結果為何。

以上各項特質沒有一項純粹屬於「AI 功能」。它們全都是標準的**平台工程架構特質**，而這正是核心要義所在。最能順利擁抱對話式介面的組織，往往不是那些擁有最多 AI 專家的團隊，而是那些**內部平台早已具備優良結構**的團隊。

## 這對平台團隊意味著什麼

這一實踐結論令人備受鼓舞。如果你的軟體目錄準確無誤、技術文件與程式碼共同維護，且所有變更均透過 Git 規範流轉，那麼為對話式介面鋪路的絕大部分工作其實已經大功告成，剩下的僅僅是介面整合工作。反之，如果這些基礎薄弱鬆散，引入對話助理不僅無法彌補缺陷，反而會以更快、更公開的方式暴露短板，因為開發者會向它提出底層平台根本無力回答的問題。

對於開發者而言，其價值在於顯著降低了邁向「鋪好之路」的門檻。尋找正確的範本或負責人不再需要依賴「懂得該去哪裡打聽」的隱性知識。對於平台團隊而言，其收益在於巨大的槓桿效應：精心編寫一次的目錄條目，如今正在持續自動回答無數疑問；當初在規範結構上投入的心力，正透過一個在結構建立之初甚至尚未存在的全新管道持續獲得豐厚回報。這正是將內嵌知識結構視為平台工程中 AI 堅實基石、而非事後補丁的最有力論據。

# 總結

本章將一個核心思想從理論推演落實為一套可運行的真實系統：**以自然語言表達的意圖，可以在完全不繞過平台團隊所依賴的任何現有管控措施的前提下，順暢轉化為受治理的平台變更。**

你從一個完全沒有任何 AI 介入的傳統平台基準線啟航：Backstage 作為開發者入口網站、Git 作為期望狀態的單一事實來源，以及 Argo CD 負責持續調諧叢集以匹配該記錄。隨後你加入了一個聊天助理，並親眼見證它因為缺乏組織專屬知識而無法回答關鍵問題。彌合這一斷層歷經了兩個關鍵步驟：目錄與 TechDocs 動作賦予了助理對宣告之平台結構的理解能力；而在同一註冊表中註冊的唯讀 Kubernetes 動作，則為其注入了對叢集即時狀態的動態感知。

你現在已能精準描述這一架構演進歷程。你親眼目睹了為什麼通用助理不能等同於平台專屬助理；理解了註冊動作如何將模型的請求轉化為狹窄受控且可稽核的呼叫；明白了完全相同的註冊動作如何發布為 MCP 工具以賦能入口網站之外的外部客戶端；也領會了助理拒絕修改 Deployment 是一項刻意的架構設計成果，而非系統缺陷。你同樣看清了依然存在的局限性輪廓：組織知識的斷層、執行期狀態的潛在陳舊、模型幻覺、多代理編排的複雜度、輸出的非確定性以及運行成本。

貫穿本章的架構參照始終如一：Kubernetes Operator 接收意圖、應用內建維運知識，並調諧叢集朝向期望狀態收斂。我們在此構建的對話層承擔了該調諧迴圈中面向使用者的前半部分職責：提示詞傳遞意圖、Pull Request 記錄期望狀態，而 Argo CD 負責最終的執行調諧。助理從不越權成為部署決策的終極權威；它成為了抵達權威的最具親和力與人性化的坦途。

這一邊界同樣構成了後續內容的出發點。本章中的一切均保持在觀察或提案層面，每一項變更都必須由人類工程師親手審查合併。下一章將全面邁入代理式 AI（Agentic AI）與自主行為的世界：系統將具備跨多步驟的自主規劃能力、在各步驟間維持持久記憶，並在更少的人工干預下執行動作——屆時，此處所提及的各項治理難題，將徹底告別理論層面，成為生死攸關的實戰課題。
